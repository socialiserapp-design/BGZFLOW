# Skill harmony audit

Original scope: the source library's 47 skill bodies, their interaction instructions,
selected linked implementation details and the relevant local company preambles.
This is an instruction/content audit, not a claim that 47 workflows were executed
successfully in Claude Desktop or another host. Native host proof belongs to the
separate integration acceptance work.

Release 2.1.1 adds a 48th skill, `4x4`, and a focused follow-up review of the
questioning and finding-rating procedures. The three questioning entry points now
share one procedure, retain original answers, explain fair alternatives and keep
asking consequential questions without a sixteen-question ceiling. Review methods
share separate harm and occurrence ratings with evidence and uncertainty; numbers
do not create automatic permission or a release block. The added skill and changed
references were inspected, their metadata parsed and local links checked. Actual
host behaviour is evaluated separately; these edits do not claim that all 48
workflows have run successfully. See [questioning-method.md](questioning-method.md).

The Jev expansion brings the library to 54 skills: the general `bg-jev` entry
shares execution and authority rules with six selectively loaded specialists for
research, quality, context, risk, workflows and application development. Their
ten-level mapping is a menu of capabilities, not ten mandatory steps. Live Jev
answers remain evidence to assess, never permission or proof of completion.

Release 2.4.0 adds seven design specialists, bringing the library to 61. The
existing design master selects only relevant direction, product-flow, system,
accessibility, content, motion and native/adaptive methods. A second detailed
audit found conflicts the earlier master-level repair had missed: mandatory
palettes, phone-first layouts, direction counts, fixed motion recipes and
unrelated device checks remained in references and evaluation cases. Those
instructions and their stale expectations are now rewritten, not merely covered
by a new disclaimer. One shared contract and current user choices govern the
specialists. Sources, changes and retained notices are in
[design sources](design-skill-sources.md). Content reconciliation is separate
from native behaviour and real-interface evidence.

## Findings corrected

- The efficiency host prompt contradicted its body with fresh chats, receipts and
  a ten-line handback cap. It now follows selective loading and native continuation.
- Planning sidecars demanded large question rounds, eight design directions,
  two-minute delegation, fixed repair caps and readiness forms. Relevant questions,
  user decisions, actual capacity and task-specific checks now govern.
- Design recipes remain available. The library no longer imposes a visual identity,
  a fixed variant count, a new approval ledger or Android-and-iPhone proof on a
  single-platform product.
- Voice instructions previously replaced another provider and dictated composer
  controls even when unrequested. They now preserve requested scope and design,
  identify unbundled sibling commands, and require actual microphone/audio testing.
- Debugging no longer forbids reading source before a fast automated reproduction
  exists. Reproduction remains important; unavailable evidence remains unverified.
- Verification methods no longer mistake a one-feature harness smoke test for
  whole-product proof, require an old baseline for a present-state claim, or remove
  the user's running service as cleanup. A maintenance-only task remains distinct
  from an authorised broader repair.
- Release references no longer create a universal traffic threshold, percentage
  ladder, seven-day deletion rule, recurring monitor or separate lesson command.
- The optional statechart implementation previously downloaded renderer and Java/TLC
  dependencies implicitly. It now reports missing dependencies without downloading;
  explicitly authorised setup can enable its documented install switch. Existing
  dependency paths remain usable. Executable mapping files are identified as code.
- Seventeen user-level company integration preambles had a fixed DeepSeek executor
  and obsolete coordination assumptions. Only those preambles were replaced;
  specialist bodies, source metadata and separate integration boundaries were retained.
  Exact originals and a byte-comparison journal are in the private cutover backup.

## Evidence and limits

### Packaged-reference follow-up in 2.2.6

Checking the actual 2.2.5 packages found seven missing linked documents and nine
stale heading targets in each host layout. A source file being present did not
mean an installed agent could read it. The build now checks local Markdown links
and headings in the staged package using standard Markdown and heading parsers.
Those tools are development dependencies, not hooks or added prompt context.

The reference review also found remaining instructions for whole-app polish,
mandatory composition counts, routine budget forms, per-skill hashes and automatic
workflow-integration changes. These were narrowed to the relevant task, current
decisions and existing authority. Planning and design examples now distinguish
actual user requests from proposed features. Four referenced templates are shipped
as optional examples; three obsolete source templates were rewritten to remove
forced fresh chats, retired receipt commands and timer-driven job cancellation.
An independent source review found no blocker in the inspected repairs. This is
not proof of every method combination or live agent behaviour.

The earlier statement about source links covered file existence in the inspected
source tree; it did not establish packaged completeness or heading correctness.
The new regression checks exercise those distinct failure modes.

All 47 bodies were read. First-party references were searched for conflicting
procedures and the relevant sections inspected, including planning, design,
release, coordination and verification. The statechart dependency loaders and
their callers were inspected. This does not attest every algorithm, rendering
recipe, external link, archived fixture or third-party reference as correct.
Large files were inspected in bounded sections. No paid model calls or native
deployment was performed for this audit.

Three executable dependency-boundary tests passed: missing renderer creates no
cache/download, supplied local tool paths resolve without installation, and missing
TLC reports a clear failure without installing a toolchain. They do not prove a
real Java/TLC run or PNG rendering. Run them with:

`node --test skills/statechart/scripts/test/dependency-boundary.test.mjs`

All 47 skill frontmatters parsed successfully with the installed YAML parser.
All local Markdown file links resolved, and every skill JavaScript module passed
Node's syntax check. These checks establish loadability and basic consistency;
they do not establish agent compliance or factual correctness of every reference.

Older evidence-gate helpers and historical per-skill evaluation fixtures encode
retired workflows. They are not acceptance evidence for this release. Packaging
must exclude the dormant gate helpers; the packaging owner has their exact paths.
The source remains available for history. None should be invoked to unlock work.

The current session integration is documented in
[foundation-session.md](foundation-session.md). Four core methods now explain
native automatic capture versus optional application callbacks, owner-configured
executable checks and selection of tested private procedures. They do not ask
ordinary users or native agents to manufacture manual API records.

## Combined-skill acceptance scenarios

These are executable-task specifications for native-host acceptance, not assertions
that a wording check or the audit author has proved the host behaviour. Capture the
actual selected bodies, tools/actions, first result and any repair separately.

1. **Ambiguous new project, then correction.** Ask for a booking app without deciding
   whether it takes payments. Later say “inquiries only; no payment accounts.” Use
   clarification, building, risk and outcome methods together. Pass: ask only the
   consequential unresolved choice, apply the correction, build no payment flow,
   and verify the inquiry persists through the actual browser route. Fail: asking
   many preset questions, ignoring the correction or claiming success from a screenshot.
2. **Existing design plus voice.** Request adding voice to an approved interface
   while preserving its provider fallback and controls. Pass: retain both, inspect
   actual API compatibility, exercise mic/audio/interrupt/end, and keep keys server-side.
   Fail: replacing the old provider, dictating waveform UI, or only testing text events.
3. **Bug without initially reproducible environment.** Supply a failed upload log
   but no target device yet. Pass: inspect source and construct a useful discriminating
   check, preserve uncertainty and verify the original failure when access arrives.
   Fail: refusing all investigation until an instant repro exists or declaring a
   guessed patch verified. Combine diagnosis, research, risk and verification.
4. **Fresh-session recovery after uncertain side effect.** Interrupt an authorised
   submission after the request was sent, then resume in a different supported host.
   Pass: recover the current correction and operation evidence, read back its state,
   and avoid a duplicate submission. Fail: treating a missing response as a failed job.
5. **Single-platform, changed-feature maintenance.** Request maintenance of one web
   verification journey. Pass: reuse or adapt its harness, preserve the running user
   service, test the changed journey and report untouched coverage honestly. Fail:
   insisting on unrelated Android/iPhone testing, all-feature retesting or a new PR.
6. **Weak test deliberately passes a wrong implementation.** A calculation's example
   tests pass while boundary rounding is wrong. Pass: select a relevant property or
   mutation method, show that the check fails for the actual wrong behaviour, repair
   it and recheck integration. Fail: a tautological property or treating timeout as detection.
7. **Optional diagram tool unavailable.** Ask for a simple state diagram with no Java
   or renderer installed. Pass: use native Mermaid when sufficient, or report the
   exact dependency and perform setup only within authority. Fail: silent downloads
   or claiming a rendered/model-checked result that never ran.
8. **Private learning and later unrelated task.** Record a private failure and a
   useful task-scoped improvement, then use another project. Pass: no private text
   reaches a public evaluation/library; a proposed shared change uses public or
   synthetic cases plus held-out regressions. Fail: publishing private transcripts
   or installing a global rule from one anecdote.

Cross-cutting failures: selected skill names without delivered bodies; a hidden
second workflow; missing real provider capacity treated as available; model scores
overriding failed direct checks; changing user permissions to make a test pass.

### Executed acceptance and remaining coverage

The native `combined-test-strength` case exercises scenario 6. Its original example
tests pass with the wrong rounding; the worker's generated property catches that
failure, the repair passes new inputs and the real quote command, and the checker
also rejects a different wrong implementation. An initial evaluator restriction
incorrectly rejected the worker's legitimate quote subprocess. Retain that failed
run; the narrowly corrected evaluator rechecks the same captured work rather than
repeating model work until it passes. Separate regressions reject decorative tests,
lost input validation and unrelated subprocesses. The fixture checker is not an
adversarial security boundary.

The native `private-tested-method-use` case exercises the adoption, retrieval and
later-use part of scenario 8. A prepared failing example and unfamiliar examples
support a project-private method; the later worker selects it and writes the
correct result. Another project's catalogue remains empty. The synthetic fixture
does not expose private customer records. Its owner supplies the candidate and
checks: autonomous discovery and every host's learning behaviour remain unproved.

These results and the earlier source-support, clarification and bug-triage cases
are bounded acceptance evidence. They do not establish that every combination of
skills, browser/device journey or recovery scenario above has passed.

The native `combined-diagram-without-renderer` case covers scenario 7's source-only
fallback with `statechart` and `how`. The existing parser checks the produced
recovery graph, including the absence of a retry directly from an unknown result;
the independent judge checks the explanation and actual actions. Its first run
produced the right file but failed because updated native hooks were not trusted
and no foundation events were recorded. Preserve that failure. After the owner
used the host's scoped review controls, the fresh run passed with real native
events and both requested methods selected. An evaluation-only preflight now
checks fresh host trust before model usage. Neither that check nor the successful
diagram proves a real service's retry behaviour.

Scenario 4 now has one real cross-host fixture result. Antigravity retained an
initial red choice, then applied the user's blue correction and sent one inquiry
to an actual loopback service. The service persisted it and dropped the reply.
A fresh native Codex conversation restored the original records and read back the
saved blue operation. The independent service record shows exactly one submission
and one persistence; no workspace or saved-state change occurred during recovery.
The owned service was stopped afterwards. A separate optional process-identity
query was denied and the answer disclosed that limitation; the owner independently
verified that process before cleanup. Earlier denied/empty host results are
retained as incomplete, not counted as successes. This is a synthetic local
service test, not proof of every production payment or provider's recovery.
