# Automatic methods and recoverable assignments

The foundation selects methods from the current request, supplies complete selected
procedures, and revisits selection when observed work changes stage. Native plans
are one signal, not a prerequisite. Editing, conventional verification commands,
research and supported real-surface tools also trigger stage selection once per
turn. Pure conversation keeps its fast path. References and assets remain on demand.

Selection compares all nominated candidates in byte-sized packets instead of
discarding everything beyond twelve entries. Complete procedure text replaces
the former short excerpt. Existing routing time/call limits still cause an honest
main-agent fallback; this is not a guarantee of perfect selection.
Packing measures the complete outgoing request, including task context, selected
methods and question text. Procedures appear once; packet winners are compared
in bounded pairs. The byte budget is a conservative heuristic, not a tokenizer.
An individually oversized or changed procedure is marked for the main agent to
assess locally. It does not discard other checked recommendations. Such routes
are explicitly partial, never described as a complete comparison. If a later
supporting comparison stops, checked recommendations remain available and the
remaining nominees stay unassessed. Unchanged partial recommendations can be
restored without paying for the same failed comparison again. If nothing was
checked, the ordinary main-agent fallback remains. Procedures are never clipped.
Fixed diagnostic categories explain failures without recording raw exceptions,
provider responses, credentials or extra personal data.

Automatic records distinguish selected methods, exact procedure context prepared
for the host, observed tool execution and verified outcomes. Prepared context does
not establish cognitive reading. Ordinary-prompt outcome evaluations inspect real
saved effects, not just method names or an agent's report.

## Recoverable work

The session adapter applies useful patterns from DeepSeek's MIT-licensed
[SuperAgent prototype](https://github.com/deepseek-ai/dsh-superagent-prototype/tree/8c32a9dc5d72c033816c6a8110b37f40cf94fba4):
preserve original assignments, queue source-identified corrections, reconcile an
uncertain delivery before retrying, and retain reservations while observed worker
or background work remains active. Delivery and consumption are separate states.
The existing assignment store is used; no parallel ledger or daemon is added.

Host integrations must supply genuine delivery and reconciliation observations.
The optional session API does not itself control every native host's workers.
Native agent follow-up events are also recovered in the existing continuity view;
an observed host return never means the worker consumed the correction.

The prototype's fixed job timeout, mandatory spare human slot, automatic small-PR
merge policy and platform-specific permissions are not adopted. It is a research
prototype, not a claim that BGZFLOW has imported a production DeepSeek service.

## Mechanical checks and boundaries

The mechanical hook recognises native patch, write and edit inputs, including
namespaced tool calls. It checks configured workspace boundaries, newly introduced
secret patterns and syntax of saved JavaScript files. Moves check both paths;
removing old secret text is allowed. Unsupported structured patches fail closed
only when a write boundary is configured. This is not a general shell sandbox.

Host permissions remain authoritative. Tools embedded in arbitrary shell or
orchestration code cannot all be intercepted by an argument hook. Host differences,
unseen tools, task interpretation and unavailable devices remain real limitations.
No new completion receipt, reply block, read receipt or forced planning step is
introduced. A successful component test is not a verified user outcome.
