# Parallel Concepts

Use this method only for the current research question. Reuse the existing brief, applicable user answers and private records; several selected methods contribute to one investigation, not repeated interviews. Inspect permitted actual evidence and preserve source links. Do not invent participants, quotations, emotions, findings, measurements or approvals; mark hypotheses and missing data explicitly. Planning a study does not authorise recruitment, messages, recording, tracking installation, spending, account changes or product changes. The current task and host permissions govern; shared automatic records are not proof that a study ran.
## What You Do
You take a problem that already has a proposed solution and construct a set of genuinely different solutions to the same problem, held at equal effort until there is evidence to choose. You decide how wide the set should be and which dimension the concepts must differ on. You do not rank or eliminate them — that is `research-owl-concept-selection`.
## Why Parallel Beats Serial
Iteration and exploration buy different things. Refining one concept improves that concept. Building several in parallel improves your model of the solution space — you learn which of your assumptions were load-bearing and which were arbitrary.
The upstream method cites parallel-prototyping research as motivation, not proof that parallel work always wins. Compare likely learning with actual effort. Possible benefits include:
- **Critique lands better.** With one design on the table, feedback reads as a verdict on the designer. With several, it reads as information about the options.
- **The first idea loses its unearned advantage.** Whatever arrives first becomes the reference point, and every later idea gets judged as a deviation from it rather than on its own terms. A parallel set removes the incumbent.
Cost depends on fidelity and shared work; do not invent a linear estimate or require parallel agents. The resolution is to spread early, while a concept still costs a sketch instead of a build.
## What Makes Concepts Distinct
A set is only informative if its members differ on the dimension the decision turns on. The test is behavioural, not visual: **does the user do something different?**
- **Sequence** — what the user is asked for first, and what waits
- **Unit of interaction** — one item at a time, a batch, or a continuous stream
- **Division of labour** — what the person decides versus what the system decides for them
- **Entry point** — where the task begins and what it assumes the user already knows
- **Commitment point** — how far in the user goes before the action becomes irreversible
For a behavioural question, recolouring the same steps may add little evidence. For a visual-identity choice, visual differences can be legitimate alternatives. Do not discard requested variants or invent a mandatory third concept.
## Sizing the Set
The count is a consequence of cost and stakes, not a target to hit:
- Several cheap sketches may answer an early question better than fewer polished mockups; neither count is required
- Concepts must sit at **comparable fidelity** — a rendered option beats a rough one on presentation alone, whatever their merits
- If you cannot say what a concept tests that the others do not, it is padding — drop it
## Best Practices
- Write the question the set has to answer before drawing anything; a set that answers no question is a portfolio, not an exploration
- Give every concept enough effort to be defensible — a deliberately weak option is a strawman and corrupts the comparison
- Keep irrelevant variables comparable when isolating behaviour. When visual identity is the actual question, vary it deliberately
- Do not carry a concept you would refuse to build; an option nobody would ship is not an option
- Not for choosing which problem to solve — that is `research-owl-opportunity-framework` (ux-strategy)
