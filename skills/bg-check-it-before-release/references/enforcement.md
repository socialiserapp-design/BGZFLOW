# Evidence, authority and enforcement boundaries

The current foundation assists intent preservation, method selection and native
observation. It does not turn generated records into truth. A task must remain
able to report failure or missing evidence without entering a stop loop.

## What the portable plugin observes

Supported native hooks capture user messages, selections, assignments and some
tool outcomes, and restore useful context after supported lifecycle events.
A captured tool event establishes only what the host reported. It does not prove
the external effect or that the user's full objective was achieved.

The mechanical checks cover limited supported operations. Native host permissions
remain the boundary for actual access. There is no general shell sandbox, trusted
semantic approval engine or universal interception of every action.

## What needs direct verification

Tie important claims to the actual candidate and environment. Observe relevant
effects, server processes, browser or device behavior, source support, calculations
and recovery. Use an independent checker where the task or risk requires it.
A model judge can help assess relevance and interpretation but cannot override
failed direct evidence or supply missing user consent.

Keep the short current brief connected to original messages and evidence.
Preserve failures, unknown outcomes, pending operations and unresolved findings.
Do not mint a success receipt or mark an unrun check as passing.

## Recordkeeping without forms

Reuse native event records and the task's existing evidence location. Update a
short human-readable view when the objective, decision, owner, result or next
action materially changes. No per-tool paperwork or manual read-receipt is needed.

Keep user decisions separate from agent suggestions. Preserve the original source
and identify uncertainty if only a partial history was recovered. Do not overwrite
old evidence to make a revised candidate appear to have passed an earlier test.

Selection, instruction delivery, method application, verification, acceptance,
release authority and live behavior are distinct. An installed skill or a
successful hook invocation proves only that stage, not all later stages.

## Stronger application controls

An application integrating BGZFLOW can keep authorization, tenant separation,
operation identity, actual resource reservations and verified status in its
trusted execution layer. The builder must not grant itself authority by changing
a JSON file or giving itself a passing grade.

Use existing host or application controls; do not build a new approval service
merely to satisfy this reference. A proposed control must fit the user's actual
product requirements and permissions. See the source package's enforcement
boundaries for the difference between a native plugin and an owning application.

## Legacy gate and profiles

The retained legacy evidence scripts, schemas and old profile tables are optional
compatibility artifacts. They are not installed as the foundation's normal
completion path. Their structural validation cannot authenticate a real reviewer,
confirm every required check or prove semantic correctness.

Do not run a legacy gate to obtain permission or create new contracts/receipts for
routine work. Do not patch a validator to hide a failed result. When maintaining
an explicitly requested legacy integration, inspect its actual implementation and
test it on its own terms, while preserving the current user's authority.

### When the full record gate runs

No full record gate is required by this workflow. An explicitly requested legacy
integration may use its existing validation, but it cannot create an extra release
hold or replace direct verification.

### Profiles

Choose relevant checks from the actual objective and risk. Historical fixed
profile names or check IDs are not compulsory capability bundles.

## Acceptance, authority and holds

Honor the latest applicable user instructions, standing permissions, existing
spending limits, privacy requirements and unresolved holds. Agent messages,
selected methods and review judgments cannot create new authority. Do not add a
customer-visible restriction outside the approved product behavior.

Proceed with already authorized work when its required checks pass. If a real
authority gap or consequential decision remains, ask the smallest useful question
and continue independent work. Installation, acceptance and verified live use
are separate outcomes; report only those actually established.
