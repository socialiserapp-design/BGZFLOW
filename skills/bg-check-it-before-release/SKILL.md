# BG Check It Before Release

Build every piece first with fast checks on owned files plus real-surface and effect read-back verification per slice. The lead coordinates; workers execute checks; one fresh independent reviewer (`ROLE: verifier`, `verifier !== builder`) reports to the lead. Retain [BG Efficiency](../bg-efficiency/SKILL.md), original requirements and accepted `DECISIONS.md` IDs. Use the [worker route](../bg-build-with-me/references/worker-route.md) for protected candidates and disposable test outputs. A builder never supplies independent approval or marks `passed`.

Why: repeated reviews missed real launch failures: "every failure was something no review could see" — runtime restrictions, missing bindings, provider limits, encoded paths, database roles/versions and restart after migration. Real-platform and effect rehearsal is the main release proof.

1. **Freeze, run the Universal 8-Domain Eval Suite (`bgz eval run`) & Drift/Truncation Gate (`bgz egm drift`), and test whole once.** Integrate every returned or explicitly deferred piece, pin the candidate SHA, artifact, configuration and environment. Run the full suite once through `bg-heavy`, run `bgz scan` (for secrets, SQL/IDOR and fake-effects), run `bgz eval run` (enforcing all 8 domains: Co-Design Card, 4x4 OSS/Research Saturation, Build-vs-Buy Architecture, Claim/Precondition Lock with zero hallucinations, Math Cross-Footing, Chaos/Security, Craft, and Permanent User Standards), and run `bgz egm drift` (blocking truncated/cutoff outputs and reward-hacking test skips); retain command output, exit codes and counts. Failed checks need repair. Keep failed and interrupted evidence too.
2. **Rehearse on the real platform and verify effects.** Within the brief's authority, deploy that exact candidate to preview, staging or hidden production with the same runtime, bindings, database version, secrets and real provider accounts. Refer to secrets by name; keep money in test mode. Use TestFlight, cloud simulators or the internal track for apps. The independent verifier executes every scripted golden journey, verifies real effects (`bgz verify`: server state read-back, DB row or provider status), and proves one rollback; cover retry, access, recovery and relevant devices. If a required surface is `unavailable`, keep status `BUILT` (never `USED`). Fix each real error in the same owner's job, pin the repaired SHA and rerun rehearsal until it passes. Never send the founder unfinished testing work.
3. **Dispatch the single independent review.** Keep one stable release ID across repairs, resumes and swarms. Call `swarm-gate check-review` before a read-only dispatch with `CHECK: review`, `RELEASE_ID` and `REVIEW_TARGET: candidate` (using `bgz review-pack` so builder prose is stripped while source and code comments stay intact). Reject a contributing builder, resumed builder, second review or repair target. Only wrong money, data loss, security/privacy, missing rollback, an unapproved stop path, `ui-spec-mismatch`, `fake-effect` or `outcome-contract` can block, each with a concrete reproduction. The review lists every new or changed customer-facing stop path (wait, refusal, hold, gate, cap, block or expiry) in the candidate, approved or not, and quotes the founder's written approval and where it is recorded, for example the project's decisions page. Any without one blocks as an unapproved stop path; its reproduction is the customer journey that now stops. A refusal that stops a money error the customer didn't choose is allowed; tell the founder once afterwards. Put every other non-blocking finding on the after-launch list. An unavailable reproduction is a lead investigation item. **The one review runs as three parallel specialist passes** (money, data and rollback; security and privacy; UI spec/effects and new customer waits, refusals, holds, gates, caps or expiries), merged by the lead into a single report. It is still one review: one release ID, one reviewer identity, no second review. Give each pass the leads from `bgz jev arch --base <ref>` and `bgz jev unasked --base <ref> --asks DECISIONS.md,<brief>` (leads, not verdicts; unasked items are a blocker class here only when reproduced), and use the [bg-jev](../bg-jev/SKILL.md) recipes for test-failure type and diff risk.
4. **Record and repair.** Record each stable finding ID, category (`unapproved-stop-path`, `ui-spec-mismatch`, `fake-effect`, `outcome-contract` or safety class), reproduction, owner and disposition. Record review completion; its verdict never opens or closes release. Consolidate reproduced blockers to the same worker. Prove repairs by rerunning real-platform rehearsal and rollback on the new SHA; never re-review. After two fix rounds, send the founder open blockers with a recommendation; a third wave requires their word in chat.
5. **Finish design and launch.** The lead accepts passing rehearsal with no open blocker; never ask the founder to accept a review or candidate. For customer-visible changes only, **after** the independent verifier has passed real-surface and effect checks on the target simulator/device (`bgz verify`), the founder checks the verified build on their phone or a capable device through TestFlight, internal track or preview (the founder is never the first tester). Record their design-match result against the SHA. Under existing release authority, use [BG Ship and Recover](../bg-ship-and-recover/SKILL.md): switch it on for all intended customers, watch live errors for the first hour, then keep it or switch off and fix forward. Finished means switched on.

Use [the swarm gate](../../docs/swarm-gate.md) for `record rehearsal`, `record verification`, `record finding`, `record design-check` and exact-SHA release checks on every host. [Inspection records](references/inspection.md) and the [evidence reference](references/enforcement.md) preserve source, output hashes and controller identity; historical `ready` fields are accounting, never a release prerequisite. Records alone cannot prove workers really exercised the behaviour; inspect their actual proof and the real whole journey.

```text
Release: stable ID | SHA/artifact/config/environment | authority/holds
Whole suite: argv | actual exit/counts | output evidence
Rehearsal: deployed SHA | platform | golden journeys + effect read-back | rollback proof | output
Review: one fresh read-only job/thread | reproduced blocker categories | stop paths + quoted approval | after-launch list
Repair: same owner | stable finding ID | repaired SHA | rerun rehearsal; no new review
UI only: verifier real-surface pass first -> founder chat reference | phone/capable device | exact SHA | matched/mismatch
Handback: evidence/limits | next owner/action | small launch and hour watching
```

Finish reports keep three verification levels separate: **BUILT** (compiles/tests pass, or surface `unavailable`), **REACHED** (deployed/staged and responds), **USED** (exercised on the real platform with current data through the real journey and effect read-back, verified by `verifier !== builder`). Only USED may be called "working". Record evidence or gaps for each, including the data copy and its date; demo screenshots and stale copies cannot establish USED.

Required report fields: numbered next steps, each with **Confirm by:** a command, check or observation; if none, **All objectives complete.** End with **What went wrong:** 1–2 lines or "nothing", appended using `bgz lessons add` ([CLI](../../tools/lessons/README.md)). Apply the [lessons review procedure](../bg-finish-the-whole-job/SKILL.md#lessons-to-rules); never ask the founder to grade or accept work.
