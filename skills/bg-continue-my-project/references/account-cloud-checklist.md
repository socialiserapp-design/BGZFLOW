# Account and cloud continuation checklist

Use with [BG Continue My Project](../SKILL.md), the [worker route](../../bg-build-with-me/references/worker-route.md), the [worker packet](../../bg-finish-the-whole-job/references/worker-packet.md) and the [glossary](../../bg-build-with-me/references/glossary.md), which also defines review verdicts. Keep receipts in the existing [checkpoint](../../../templates/CHECKPOINT.md). The founder's recorded decisions (the project's `DECISIONS.md` or the overlay `FOUNDER.md`) govern accounts, spending and cloud use, and the founder's account aliases and plans live in the overlay `ROUTES.md`. This checklist grants no new authority: an account change, upload, cloud run or extra spend needs the founder's direction.

## Account lifecycle

1. **Observe → usage row.** Before material dispatch, at meaningful checkpoints and near the agreed ceiling, read the host's supported usage display once. Record the provider, the exact known non-secret account alias, allowance, window and reset, the observation time (from the system clock) and source, shared limits, project ceiling and reserve. Label every figure `observed`, `reported` (with the report's date), `estimated` or `unknown`. Never invent a quota or alias, poll automatically, or assume that changing model restores allowance.
2. **Allocate → capacity decision.** Fit ready work within the once-agreed per-account ceiling and the actual tool capacity. Keep running work and an incident reserve. Cap each brief in minutes, KB and repair rounds, never with a condition nobody can enforce. If the next material job may exceed the ceiling, hold that dispatch and ask once for the missing capacity choice; continue other eligible work within authority. Never silently switch provider, buy credit or fall back to a paid API.
3. **Recommend → exact account instruction.** Recommend the exact known available alias from the current account record, with dated evidence for its remaining usage: "Log out of [current exact alias] and log into [known target exact alias]; [observed usage and reset] supports [next task]." If an alias or usage figure is missing, record the gap and ask once for it. Never invent an account name or signed-in profile.
4. **Sign in routinely → same task, same session.** Agents handle routine sign-in and reauthentication with saved sessions, browser autofill or an existing password-manager entry wherever supported. Change account only on the founder's explicit direction, using the same tools, and keep the same task, session and account scope. Involve the founder only for a required human step. Refer to secrets by name; inject a value only into the authorised service or process, never into a prompt, log, URL or source file.
5. **Preserve → pre-switch checkpoint.** Every job runs from its own worktree, never the lead's folder, and commits its work before every account switch: ending a lead session can cancel jobs started from the lead's own folder. Commit or snapshot the project state folder (`<project>/.bgzflow/`) as well. Save the lead session ID or worker thread ID, job, turn and request IDs, original launch cwd, owned worktree, branch, commit, dirty and untracked files, actual result location, accepted scope and design, holds, findings and repair count, pending effects and next action. Store essential results outside any rolling job index. Keep credentials and authentication data out.
6. **Fence → owner and effects decision.** Decide whether each old job is active, terminal or uncertain by checking its record against the live process: `running` or `queued` with a dead process is uncertain, not active. Cancel a job queued for more than 5 minutes and redispatch it only after reconciling it. Reconcile pending commands, paid or external requests, local processes and resource ownership, and clean up the resources a job created (named with its job ID prefix) before any retry. Prevent concurrent dispatch by the old and successor owners. A timeout or closed window is not cancellation, and a replay to find out is never allowed. Keep the working recovery path.
7. **Resume → actual identity receipt.** After any sign-in, reauthentication or authorised account change, verify the account alias, access and usage through supported controls. Match the same lead session or worker thread and the exact-target rules in the [worker route](../../bg-build-with-me/references/worker-route.md) before continuing. Match the original launch cwd; never assume a "resume last" option picks the intended worker, or that a new folder relocates the parent folder's state. Record expected and observed identity, executor and exit status, plus a harmless real resumed read or result. A retained transcript or sidebar entry alone does not prove continuation.
8. **Resolve failure → scoped handoff.** If same-session resume is unsupported, preserve the work and hold only the affected continuation. Request supported continuation or a terminal-job ownership handoff: old job terminal, pending effects reconciled, old dispatch fenced, and a named successor owning the exact candidate, findings and remaining repairs. Label the successor honestly; it is not same-thread proof. Never edit sidebar indexes, profiles, plugin state or live transcripts.

An account-switch route stays `pending` until actual before-and-after identity and resumed-execution evidence exist. The lead owns that qualification and records its status in the overlay `ROUTES.md`. Never recommend a fabricated account.

## Local background versus PC-off cloud

| Route | What must be proven | Without proof |
|---|---|---|
| Local background job | Exact local job and thread, owner, cwd, result and wait route, and that the machine is available | Checkpoint for the PC's return; background never implies execution after shutdown |
| Included cloud (part of an existing plan) | Entitlement and allowance with no additional spend; scoped private repository and version; environment, dependencies, tools and secret access; sole writer; exact return route | Keep eligible work ready with the missing proof named; no upload or cloud job |
| Signing, emulator, device or local-file work | The required PC resources, local authority and recovery are available | Set `worker_state: waiting-for-PC`; name the resource owner and the wake or resume condition |

1. **Qualify eligibility → cloud admission row.** Verify the exact included service, account and task entitlement, the usage ceiling and zero additional spend. Check that the private repository is already accessible under existing authority at the exact commit; a decision allowing cloud work does not prove the repository is there. Verify environment, dependency and tool compatibility, network scope and approved secret-store references without exposing secrets or customer data. Identify local files, emulators, signing and devices, and keep those steps `waiting-for-PC`.
2. **Transfer safely → one-writer handoff.** Reconcile local jobs and effects first. Pin the task and requirements, contracts, skills and read access, immutable base, branch and path ownership, remaining findings, output and test commands, and rollback or containment. Pre-authorise push in the cloud worker's brief, or have it commit to its branch every N minutes (N set in the brief). Fence the local writer before an authorised cloud successor starts. Never run concurrent local and cloud writers for one resource or invent a new orchestration service.
3. **Bind return → cloud result route.** Record the actual cloud job or session, owner, source, configuration and environment, result, patch or artifact location, destination integration writer and supported completion control. Before relying on unattended execution, verify that a real result reaches the lead and can be retrieved after the PC returns. A queued task or configured integration is not that proof. Keep the existing working recovery while qualification is incomplete.
4. **Reconcile on return → combined checkpoint.** Collect exact cloud outcomes and surviving local jobs before resuming. Compare base, branch, dirty and untracked files, pending effects and owner authority. The sole integration writer inspects scoped changes, resolves conflicts with their owners, merges immutable candidates and reruns affected and whole-candidate checks. Resume PC-bound steps when their resources return, and obtain a fresh independent whole-candidate verdict. Keep deployed recovery and release holds unchanged.

## Copyable qualification receipt

```text
Task/requirement IDs; route local-background/included-cloud; owner; authority/holds.
Account exact alias or gap; usage observed/reported/estimated/unknown; source/time/reset; ceiling/reserve; no-extra-spend evidence.
Expected/observed lead session or worker thread; job/request; executor; exit status; original cwd/worktree.
Pre/post switch branch/commit/dirty files; state folder committed or snapshotted; pending effects; fenced owner; resumed result.
Cloud entitlement/repo/commit/env/tools; secret-store refs by name; push pre-authorised or commit every N minutes; qualification result/gap.
Local-only steps: waiting-for-PC | resource/owner | actual resume trigger.
Return: exact result/artifact/check outputs/hashes | integration writer | received evidence.
Recovery retained; next action/owner; account-switch route pending/proven with evidence.
```

Qualify each of these boundaries on authorised, lower-risk real work, and keep unknowns labelled until then.
