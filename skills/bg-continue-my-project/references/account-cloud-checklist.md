# Continue across account or execution changes

Use current project decisions, the existing task record and the actual host's
supported controls. This BGZFLOW-authored reference adds no account change,
subscription, upload, background service or spending authority.

## Before a material change

Inspect the actual signed-in account and available allowance without printing
credentials. Distinguish observed capacity from reported or unknown capacity;
several model names on one account do not create several independent worker slots.
Choose from available routes within the user's current instructions and spending
limits. Reuse standing approval when it still covers the action. Do not silently
switch accounts or buy capacity when a route becomes unavailable.

Preserve current decisions, owned files, pending operations and useful evidence.
Use native continuation and automatic records where supported. A forced commit,
fresh chat or separate qualification receipt is not required. Never commit private
state or credentials merely to carry out an account switch.

## Ownership and unknown effects

Identify each old job through its actual native identity and current status.
Queued, failed, completed and uncertain are different states. A missing process
or closed window alone does not establish whether an external request succeeded.
Reconcile the original operation before retrying or transferring its ownership.
Do not cancel a queued task because an arbitrary timer elapsed. Keep one writer
for each shared resource and close only temporary resources this task owns.

Use supported reauthentication with existing saved credentials when authorised.
Involve the user for a human-only step or an unresolved account choice. After a
change, verify the intended account, task, workspace and a harmless resumed action.
A sidebar entry or saved transcript alone does not prove execution resumed.

If same-session continuation is unavailable, state that limit. Preserve work,
reconcile the former writer and pending effects, then use a supported successor
handoff when authorised. Do not edit native chat indexes or pretend that a new
session is the old one.

## Local versus cloud work

A local background job requires its machine to remain available. It does not
continue after shutdown. Remote work requires a supported service, actual capacity,
permitted repository/data access, compatible tools and a return route. Verify those
facts before relying on unattended execution; a subscription name is insufficient.

Send only the necessary allowed source and task context. Preserve one writer and
explicit output ownership. Confirm that a returned patch or artifact belongs to
the requested candidate; inspect it before integration and run relevant combined
checks. Keep local-only device, signing or private-data work separate from remote
work. Missing capacity holds only the affected contribution, not the whole project.

Record meaningful changes in the existing brief, using native job observations
where available. Include the next owner/action and any unresolved effect. There
is no required schema, fixed byte limit, periodic commit or second approval form.
