# Build with me

Understand the result the user wants, including audience, environment, constraints and what would demonstrate success. Inspect existing work and decisions. Ask only about consequential unknown choices; investigate discoverable facts yourself. Bring useful alternatives and missing professional considerations to the user without silently expanding the brief.

For substantial work, keep one concise current plan. Preserve the original request and corrections separately from your interpretation. State what will be delivered and how its real effect will be checked. Reuse the project's existing record rather than adding a competing board. Revisit understanding when prototypes reveal a choice, new constraints arrive, evidence contradicts an assumption or a failed check exposes a different expectation. Ask before dependent work and visibly use the answer. Load bg-outcome-evals when designing consequential completion checks.

Use BGZFLOW's catalogue and Jev routing when available. Choose from the user's actual available tools and providers. If routing is unavailable, select directly from the same catalogue and proceed within authority. Read relevant skill bodies before applying them; honour explicit requested skills. Select methods again when the task, stage, capability pool or failed approach materially changes. Do not run a fixed council or load every skill.

Use a single agent for tightly connected work. Delegate independent work when it improves the outcome within the task's time and usage choice. Give each worker the relevant request, current decisions, owned work, success checks and permitted effects. Keep one writer for each shared change. Use a fresh independent checker where consequence or complexity warrants it; another provider is optional.

For implementation work, use the [integration and real-use loop](../bg-finish-the-whole-job/references/integration-and-real-use.md) from the first usable slice. Name the owner of integration, installation and actual testing before dispatch. A worker's handback starts that loop; it does not complete the user's request. Keep accepted work moving into the real app within existing authority while unrelated workers continue. Use the host's supported completion events and check that they reach the lead; a saved handback or a skill file does not wake an idle agent.

Execute complete usable pieces. Use existing packages and project interfaces when they fit, checking current compatibility and licensing. A custom component needs a concrete gap that existing options do not meet; routine glue is normal engineering. Never turn a speculative improvement into unrequested work.

Proactively compare the intended outcome with the capabilities actually available: required operations, verification surfaces, data, tools and expertise. If something needed is missing, investigate existing open-source packages and supported services without waiting for the user to name a tool. Compare fit, compatibility, maintenance, licence, privacy, integration effort and cost. Install or adapt a suitable option within existing engineering authority and verify that it closes the gap on the real task. Ask only when a material product trade-off, new spending, sensitive access or other unresolved authority is needed. Keep the affected step explicitly unverified if no adequate option is available, and continue independent work. This is task-driven discovery, not an always-on research loop or permission to build unrelated infrastructure.

Inspect actual tool results. A timeout or lost response is an unknown effect, not permission to repeat it. Reconcile the original operation before retrying anything externally visible or paid. If an approach fails repeatedly, diagnose what changed and choose a different supported approach; do not keep retrying or impose an arbitrary global stop.

Check the intended end-to-end result in its real environment. For software this includes the actual running instance, relevant user journey and resulting state; for research it includes the supporting sources; for creative work it includes the agreed brief and intended use. Report what was accomplished, the meaningful evidence and any limitation. Do not call the overall goal complete because one component passed.

Before reporting a software feature or repair complete, automatically read and apply [the full-spectrum audit](../bg-full-spectrum-audit/SKILL.md) at the scope the work needs; the user need not name it. Review a feature's complete journey and wider effects, or a repair's cause, callers and regressions. Reserve a whole-product/codebase audit for that request or a demonstrated wider issue. Challenge missing needs and better approaches within that scope, not just changed lines. Reuse applicable evidence; recheck affected behaviour after repairs. This is the existing completion check, not another release gate or permission to redesign the product.

[Expo testing](../bg-expo-testing/SKILL.md) is a separate optional capability. Include it when the affected app is compatible and its workflow, account, test data and spending authority are configured. Inspect and use the existing setup instead of installing it again. Report unavailable coverage and continue other checks. Audit and Expo testing can each run independently; neither requires the other.

Continue in the same conversation using native compaction. Restore current decisions, owners and pending operations after compaction or interruption. A fresh worker may be useful for an independent assignment; a new chat is never required merely because a transcript file grew.

A selected skill supplies a method, not extra permission. Follow the user's latest request, existing decisions and host permissions. Use the shared task context and native tools; do not create a parallel tracker or demand paperwork. A method being selected or loaded does not prove its result.

## Integrate through supported capabilities

Use the native host's actual recording, execution, selection and check tools.
Applications embedding the foundation can connect `createFoundationSession` to
trusted host callbacks for source confirmation, capacity, owned paths, execution
and outcome observation. Those callbacks are application integration work, not
paperwork for every user request. See `docs/foundation-session.md` in the source
package. Do not claim those controls exist in a host merely because this skill
names them; missing adapters remain explicit capability limits.
