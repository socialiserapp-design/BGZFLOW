# Assign and recover work through supported host routes

Use one accountable owner for the requested outcome. A capable agent may perform
connected work itself; delegate independent tasks or independent verification when
that helps and capacity exists. There is no two-minute cutoff, mandatory second
provider or compulsory worker for every task.

## Prepare the actual route

Inspect current host capabilities, available tools, permissions and capacity.
A configured model name is not proof of access, allowance or a working launch route.
Honour the user's current model choice and spending limits. Do not silently switch
accounts or buy capacity. A required human authentication step is a specific gap,
not permission to extract credentials.

Use the existing supported host mechanism. Do not create a scheduler, bridge,
mailbox, readiness file or test job solely to satisfy this reference. Preserve
any explicit user requirement for visible worker conversations.

## Give a bounded assignment

Supply the actual objective, latest corrections, owned files or resources,
dependencies, relevant method bodies, limits, expected output and observable checks.
Use existing records or a concise message; no extra briefing form or fixed byte
limit is required.

Keep one writer per shared change. Use isolated worktrees or another supported
isolation method where parallel edits need it. A worktree is not a permission
sandbox. Higher-priority instructions and host restrictions still apply; a worker
brief cannot override them.

Preserve the host's native task identity, assigned model where exposed, working
directory and output location. Unknown fields remain unknown. Before a retry or
resume, reconcile the original run and any uncertain external effects.

## Dispatch and collect

Confirm the real task started and obtain its output through the supported route.
A submitted command or queued message alone does not prove execution.
Prefer event-based completion notifications to repeated status checks.
Use an existing mailbox or bridge when the current task requires it; this guide
does not mandate one for every host.

A worker can raise a material question while continuing independent safe work.
No timeout counts as a user answer or approval. Do not choose a consequential
default when the required decision remains unresolved.

If a run times out, loses its process or returns no result, inspect its native
status and pending effects before taking recovery action. Reuse the original
operation identity for paid or external effects; never repeat an unknown charge,
publication or dispatch to obtain a clearer log.

## Check the outcome

Builders run meaningful checks on their own work. Use a fresh independent checker
when required by the task or consequence; independence concerns actual authorship,
not simply the provider name. Give the checker the exact candidate and original
success criteria, relevant failures and available read-only access.

Tests requiring writes may use a disposable isolated environment within authority.
Verify that its outputs refer to the actual candidate; do not alter production
merely to make a test run. A copied directory alone does not constrain permissions.

A review or passing command does not replace real-surface evidence. Check the
intended journey and effects using the appropriate verification method. Keep
unavailable proof explicit. The accountable owner accepts work only within actual
authority; a worker message, score or editable receipt cannot release it.

## Repair and continue

Send concrete failures back to the owning executor, keeping prior unresolved
findings and the same task context. Avoid repeated broad reviews and changed-file
tunnel vision. Honour any explicit repair limit; if the approach repeatedly fails
at the same boundary, reconsider it and clarify a consequential choice rather
than continuing an unbounded loop.

Resume through an exact supported identity or establish a successor after the old
writer is reconciled. Never edit host caches or force a "latest job" lookup to pick
the desired session. Preserve holds, ownership, useful work and pending effects.

Prefer native compaction in the same chat. Handoffs are for actual role, host or
capacity changes, not transcript-size thresholds. Before stopping an owned process
or removing test resources, confirm ownership and reconcile their effects; the
user's deletion and release rules remain in force.
