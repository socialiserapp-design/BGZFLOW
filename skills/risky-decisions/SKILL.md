# Check consequential decisions

Trace what depends on the part being changed: callers, shared state, user journeys, document definitions, calculations or external commitments. Use actual examples and current sources rather than imagined data shapes.

Identify what must remain true: existing permissions, user choices, money/account ownership, data integrity, privacy, compatible interfaces and recovery behaviour. Tailor the checks to the actual domain and consequence; there is no universal importer count or approval score.

Compare realistic failure and recovery paths. State the assumption whose failure would matter most, then test or investigate it. Keep the user involved where a consequential preference or authority is unresolved; own routine engineering choices within the brief.

Use domain-specific expertise and sources for professional work. A generic risk checklist cannot certify law, medicine or financial advice. Separate supported facts, interpretation and uncertainty.

Describe material risks using the existing review's
[shared impact ratings](../interrogate/references/impact-ratings.md): harm 1–10
and how often 1–10 separately, with stated exposure scope, evidence and unknowns.
Include harmful or misleading claims in documents and marketing, not just code.
Keep affected people/data/money, recovery and urgency explicit; a rare catastrophe
must not disappear into an averaged or multiplied score.

Explain meaningful residual uncertainty briefly. Do not create a mandatory confession, threshold-based gate or parallel decision ledger.

A selected skill supplies a method, not extra permission. Follow the user's latest request, existing decisions and host permissions. Use the shared task context and native tools; do not create a parallel tracker or demand paperwork. A method being selected or loaded does not prove its result.
