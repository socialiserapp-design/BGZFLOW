# OTA updates and health

Use for compatible JavaScript and asset updates to an accepted installed app. Every role uses this procedure, whichever provider runs it. The terms (runtime version, channel, branch, update group) follow common over-the-air services such as Expo EAS Update; map them to the service in use. **No store submission, deploy, rollout or live-service change without the founder's existing approval.** Record its source, target, percentage ceiling and recovery scope, and reuse an approval that already covers the action. Acceptance or this reference grants no new authority. Payment, store submission and live trading happen only when the brief names them.

1. **Prove compatibility.** Compare the accepted diff with each installed platform's native binary. Never send a native change over the air: native dependencies, SDK changes, permissions and native configuration need a new build and the [store release path](app-store-release.md). Record the runtime-version policy and its resolved value per platform. Preserve the existing policy; any policy change needs its own compatibility decision. Do not relabel incompatible code to match an older runtime or bypass launch safeguards.
2. **Bind the destination.** Record the project and account, environment, binary and build ID, embedded update, channel, branch, runtime, and the update group and artifact hashes. A channel is the build's stable delivery target; its server mapping selects a branch of updates. Verify platform and runtime matching and the current mapping, including any active rollout. Changing that mapping can affect every build on the channel. Reconcile existing publish operation IDs before retrying.
3. **Prove the same artifact in staging.** Use a release-like binary with the matching runtime. Check download, cold launch, offline launch, restart and recovery. Record the actual running update ID; a downloaded bundle may run only on a later cold launch. Promote the tested artifact through the supported route. If environment differences change its bytes, inspect and test the resulting candidate again. Name any staging channel or branch a job creates with the job ID prefix, record it and clean it up before a retry.
4. **Choose exposure.** Below about 1,000 daily active users per platform, publish to everyone and watch live errors for one hour ([rollout rules](flags-and-staged-rollout.md)). Above that, use percentage controls with metric gates: plan 1/5/25/50/100 percent or a service-supported ladder. Record each actual percentage, cohort, start time (system clock), observation window, minimum sample and decision owner. Do not start a competing rollout; resolve the active one with its supported controls first. If percentage controls are missing, agree an explicitly bounded alternative plan before release.
5. **Check adoption and health.** Compare the candidate with the prior healthy update by platform and runtime over comparable windows. Record eligible devices, confirmed running users, embedded and OTA share, download failures, failed launches, and crash-free sessions or users with their denominators. Define absolute and relative stop thresholds before rollout. Aggregate update insights can lag, undercount or measure downloads rather than confirmed runs; use the app's own crash and session telemetry too. Zero traffic, absent signals or insufficient samples mean hold, not healthy. Stop expansion on a breached gate or an unexplained platform asymmetry.
6. **Recover and verify.** Within the recorded recovery authority, end or revert the active rollout as the service requires, then roll back by republishing the previous verified compatible update. Preserve its original ID and record the new publish ID. Do not rebuild old source and assume identical bytes. If no safe prior update exists, use a verified embedded-update recovery only where supported and compatible. Check actual clients after restart, adoption and restored health; offline clients may recover later. Rollback does not reverse backend migrations, charges or data loss.

```text
Handback: exact update/build/runtime/channel/branch | percentage and observed adoption | gate evidence | previous/recovery IDs | pending clients | authority | next owner
```

Inspect the installed CLI help and the applicable SDK documentation before running commands; no automatic installs, feedback sends or paid-service use. Disregard historical provider defaults in specialist wrappers; this procedure governs.
