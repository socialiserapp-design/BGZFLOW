# App-store release

Every role follows the same evidence ladder, whichever provider runs it. **No store submission, deploy, rollout or live-service change without the founder's existing approval.** Store submission, payment and live trading also happen only when the brief names them. Bind approval to the store, account and app, the exact candidate, track, territories, release timing and recovery scope. Reuse a valid existing approval; a build or tester pass never grants submission authority.

1. **Prepare the build.** Record the source commit, dependency and configuration hashes, app and bundle identifiers, environment and build profile. Keep development, internal preview and production profiles distinct; a development client is not a store binary. Inspect signing credentials, certificate and profile expiry, team ownership, the Android upload key and store account roles. Use saved approved credentials by name; never put secret values in source, logs, review notes or URLs. Do not create accounts, rotate keys or incur new charges implicitly.
2. **Verify versioning in the artifact.** Record the public version plus the unique iOS build number and Android versionCode. Reconcile local and remote counters with the actual signed archive or bundle; reject duplicate or regressed numbers. Bind the build ID, artifact hash, platform, signing identity and the accepted `DECISIONS.md` IDs verified in this artifact to the independent acceptance result. A changed build or configuration needs the appropriate recheck.
3. **Exercise internal testing.** Install the candidate on supported devices. Include constrained Android and iPhone journeys, startup, login, offline and retry, upgrades, access, accessibility and any purchases, using authorised test accounts. For iOS beta distribution (TestFlight), verify processing and compliance status, the assigned tester group and the actual installation; external testing may need beta review. For Google Play, verify the chosen internal, closed or open track, the eligible testers and the installed version. Upload success or a queued submission proves none of these.
4. **Prepare the listing.** Check the name, description, category, support and privacy links, age and content ratings, data declarations, pricing and availability against the real app. Build a screenshot matrix per store, supported device family and locale: required dimensions and count, captured version, asset path and hash, and reviewer. Check the store's current requirements when executing; avoid frozen size tables. Screenshots show the accepted experience without private data. Record missing locales or assets as blockers. Review notes explain test access through the store's secure mechanism, unusual permissions, backend availability, feature discovery and purchase review steps.
5. **Submit and observe each rung.** Under existing approval, submit the exact build and record the build and submission IDs and the store response. Reconcile that ID before retrying a timeout. Track processing, tester availability, submitted-for-review, review decision, release scheduling and public availability separately. Repair rejection reasons with the same owner. "Queued", "accepted upload" and "approved for release" are never "live".
6. **Release and verify.** Release to all approved territories once rehearsal passes. Use phased release or a staged track rollout only where traffic can measure it ([rollout rules](flags-and-staged-rollout.md)), with a monitoring owner and pause triggers. Verify the public listing and the customer journeys of an actual store-installed version. Pausing expansion does not remove binaries already installed, and users may update manually. Prepare a compatible feature disablement or a new corrective binary; stores may not support downgrading installations. Route native fixes through a compatible new store build and real-device rehearsal; never another independent review of a repair or an incompatible over-the-air update.

```text
Release record: store/app/account | candidate/build/hash/version | operation IDs | furthest verified rung and UTC time (system clock) | listing/screenshot review | tester/device evidence | phase/health | unresolved rejection or recovery | next owner
```

Optional specialist, if installed: a store-release skill such as `eas-app-stores`, with its TestFlight, iOS, Play and metadata references. Use the project's supported store tooling or console; a particular tool is an optional route, not a required worker or service. Check installed tool versions. This guide installs no skills or CLIs and authorises no auto-submit or feedback transmission.

Basis: the public [Expo eas-app-stores skill](https://github.com/expo/skills/tree/main/plugins/expo/skills/eas-app-stores), version 1.1.0, MIT; independently written procedure with project-specific evidence gates.
