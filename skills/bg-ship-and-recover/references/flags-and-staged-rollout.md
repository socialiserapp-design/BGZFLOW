# Feature switches and rollout

**Finished means switched on.** A feature or fix is not done while its intended customers cannot use it. A switch is a safety tool for the first hour, not a place to park finished work. Built-but-off work is reported as not done.

**Authority.** Deploys, store submissions and live-service changes happen within the release authority recorded for the project. Payments, store submission and live trading need the brief to name them. When that authority exists, switching an accepted feature on is part of the release: the lead does it without asking the founder again. Keeping a finished feature off needs a founder decision on record (their words and date) in the project's decisions file. Leads never invent holds.

1. **Decide what needs a switch.** Add one only for a risky new path: money, data, security, an external dependency or a migration. Plain UI and copy changes ship without one. Reuse an existing switch only if it covers every entry point. A switch never replaces access checks, entitlements, financial limits or migration compatibility.
2. **Switch on the moment it is ready, never on a later date.** Every switch has an owner. As soon as the work is built, its real-platform rehearsal runs; when that passes, it goes on. Work that is finished but still off after 24 hours appears in project status as "overdue: switch on or say why", with one recommendation for the founder. The off position must keep a verified safe existing path; test on, off and unavailable configuration.
3. **Switch on for everyone after rehearsal.** Once the exact candidate passes real-platform rehearsal and the one review has no open blocker, deploy with the switch on for all intended customers. Verify the deployed identity and the customer journeys, then watch live errors for one hour. Healthy: keep it on. Failing: switch it off, fix forward and rehearse again.
4. **Percentage ladders only where traffic can measure them.** Below about 1,000 daily active users per platform, a 1/5/25/50/100% ladder cannot reach a meaningful sample and only delays release, so use step 3. Above that, propose the ladder with pre-agreed limits (error and crash-free rate, latency, task completion, money and data invariants), a minimum sample and an observation window per stage. Too little data at a stage means extend the window once, then decide with the one-hour error watch. It never means holding indefinitely.
5. **Keep a proven kill switch for money, data and security paths.** Record who can turn it off, how fast that propagates without a new deploy, and test it, including stale or offline clients and in-flight work. Where a client switch cannot stop dangerous writes, add a server-side control. Turning a feature off is not a refund or a trade reversal; preserve payment and order IDs.
6. **Remove the switch after 7 healthy days.** Delete the switch and the old code path in a compatible order, including for supported older app versions. Run the relevant tests and check that nothing still reads it. Keep only deliberate permanent kill switches, each with a named owner. Stale switches are a known cause of serious incidents; one dormant switch cost Knight Capital about $440M in 45 minutes in 2012.

Record per release: switch key | owner | built (time) | rehearsal result | switched on (time) | one-hour error watch | kept or contained | removal date.

Optional services, where available: an existing configuration service or a hosted flag service (for example PostHog, GrowthBook or LaunchDarkly). Over-the-air channel delivery is a separate artifact control, not a substitute for a runtime switch. Do not install a flag service implicitly. An optional OTA skill such as `eas-update` applies only to the [OTA path](ota-updates.md).

Basis: LaunchDarkly's [flag decision, guarded rollout, cleanup and drift skills](https://github.com/launchdarkly/ai-tooling/tree/ef549715fe267e6027ba9172819205621b58eee1/skills/feature-flags) (Apache-2.0), adapted for small teams with low traffic. Further sources: Pete Hodgson, [Feature Toggles](https://martinfowler.com/articles/feature-toggles.html), on keeping release toggles short-lived; Uber, [Piranha](https://www.uber.com/blog/piranha/), on stale-flag debt; and Knight Capital's [2012 filing](https://www.sec.gov/Archives/edgar/data/0001060749/000119312512346917/d361681d10q.htm). All steps are in our own wording.
