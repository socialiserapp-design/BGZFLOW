# Feature flags and guarded rollout

Use one contract across projects and providers. **No store submission, deploy, rollout or live-service change without the founder's existing approval.** Record the approved environment, cohort, maximum exposure, metric gates and containment authority. A flag recommendation is read-only until the actual instruction permits mutation. Payment, store submission and live trading happen only when the brief names them.

1. **Decide what needs guarding.** Inspect the affected callers and customer behaviour. Guard new or changed risky paths, migrations and external dependencies. Reuse an existing flag only if it covers every affected entry point and still protects. Record a verdict (new flag, reuse, already guarded or not applicable) with evidence, an owner and an expiry date. A flag never replaces access checks, entitlements, financial limits or migration compatibility.
2. **Default off.** Keep the new behaviour off in the code fallback, in missing or invalid configuration, in the initial server state and in offline or uninitialised clients. Off preserves a verified safe existing path. Test on and off, unavailable configuration and stale cached values in every critical environment. Do not copy a remote "on" default into code merely to remove drift; document intentional safe-fallback differences. Client flags never authorise privileged server actions.
3. **Prove a kill switch.** Record how the authorised operator disables the affected behaviour independently of a new deploy, who can operate it and the expected propagation bound. Test it safely, including stale and offline clients and in-flight work. Where client propagation cannot stop dangerous writes, require a server-side control before rollout. Show that a scheduled expansion also stops; pausing a schedule alone does not turn an enabled feature off. Keep unresolved payment and order IDs: disabling a feature is not a refund or a trade reversal, and a code rollback does not reverse money or data changes.
4. **Precommit the gates.** Record the baseline or control and candidate cohorts, assignment unit, stable bucketing, platform and runtime split, denominators, telemetry lag, minimum sample, observation window, absolute limits and allowed regression. Include error and crash-free rate, latency and task completion, plus access, data and money invariants as applicable. For a wholly new feature with no comparable off-path, use service-wide safety signals and direct journey evidence. Verify alerts, the monitoring owner and the rollback action before exposure.
5. **Advance only on evidence.** Start with an authorised internal cohort. Propose a 1/5/25/50/100 percent ladder, adapted to the supported controls and the approved risk. At each stage record the actual exposure, window, sample, measured values and a pass, hold or recover decision. All gates must pass before expansion. Missing, delayed, zero-volume or insufficient telemetry means hold. A breached safety invariant triggers containment under existing authority; a breached metric triggers the recorded stop or rollback action. Automatic rollback, where available, needs the same advance authorisation and a safe test; otherwise an available operator owns it. Never advance unattended without working monitoring and recovery.
6. **Clean up.** After sustained acceptance and the recovery window, enumerate flag evaluations, environment rules, defaults, experiments, telemetry and dependencies, including supported older mobile binaries. Obtain the existing owner's release decision, remove the obsolete branch and flag in a compatible order, run the relevant tests and verify that no caller still relies on it. Archive the decision and evidence and close the expiry task. Keep permanent operational kill switches explicitly owned and tested.

```text
Gate record (fill before use; a blank gate never means pass):
flag/key and candidate | stable cohort (e.g. 5%) | baseline and limits | minimum sessions and time window
observed values | decision and UTC time (system clock) | operator | kill-switch proof | approval reference
```

Optional services, where available: an existing configuration service or a hosted flag service (e.g. PostHog, GrowthBook, LaunchDarkly). Over-the-air channel delivery is a separate artifact control, not a substitute for a runtime feature flag. No flag specialist is assumed; do not install one implicitly. An optional OTA skill such as `eas-update` applies only to the [OTA path](ota-updates.md).

Basis: LaunchDarkly's [flag decision, guarded rollout, cleanup and drift skills](https://github.com/launchdarkly/ai-tooling/tree/ef549715fe267e6027ba9172819205621b58eee1/skills/feature-flags) (Apache-2.0), read at that pinned commit. All steps are our own wording; no hosted MCP dependency, vendor worker rule or upstream automatic mutation is inherited.
