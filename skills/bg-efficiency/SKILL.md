# BG Efficiency

## When to use

Apply throughout every BG stage and assignment. Optimise time and cost per accepted outcome while keeping requirements, meaningful tests, commercial quality and holds. Use the existing [glossary](../bg-build-with-me/references/glossary.md). This is the shared efficiency guide. It distils several efficiency tools (terse output, lean code, command-output filtering, cached reads and context compaction); their provenance and adaptations are in [sources](references/sources.md) and the [source manifest](references/source-manifest.json). Read sources only as needed.

BGZFLOW's own commands (`notes-map`, `startup-check`, `bg-rounds`, `bg-heavy`, `bg-swarm`, `doctor`) ship with this plugin. Run one as `node "${CLAUDE_PLUGIN_ROOT}/tools/<name>/<name>.mjs"`; where the host leaves that path unfilled, the plugin root is two folders above this skill's folder.

## Numbered checklist

1. **Recover only relevant context → retained-context record.** Read notes and history through the notes map (`notes-map ask "<question>"`; build it with `notes-map build <folder>`; if unavailable, `rg -n` on headings) and code through a code map when one is installed (CodeGraph or graft). Never open a notes or log file over BGZFLOW_BIG_READ_KB (default 64 KB) whole. Check the repository, worktree and candidate commit; sync the code map before the first query batch and again after edits, checkout, rebase or a stale warning; query exact names and read only the needed lines. [Tool harmony](references/tool-harmony.md) holds the commands, the rules by role and which tool owns which job. If the map errors or returns an ambiguous, incomplete or empty answer, go straight to a targeted `rg -n` and a source read, and record why: an empty answer never proves there is no caller or test and never waives a test, caller check or hold. Read the map, one-page checkpoint, accepted decisions, owners and affected contracts and callers. Keep unresolved failures. Keep stable instructions first and changing task facts after them, for prompt caching. Do not load whole libraries or reread logs. Record per session the map's returned output volume in characters, separately from source reads and elapsed time.
2. **Select and prove guidance → skill-read matrix.** Apply [capability coverage](../bg-build-with-me/references/capability-coverage.md) and the bounded [skill selection](../bg-build-with-me/references/skill-selection.md); this skill is the only compulsory efficiency body. The source tools stay optional, on demand. Reuse matching unchanged selections. When a selection route fails, record one fallback selection and routing judgment and continue safe work, with no paid retry or per-message loop. Supply full selected bodies or verified access to each executor. Record body path, hash and read receipt separately from actual application, tool or hook execution and gaps. Use code for exact hashes, counts, joins and paths.
3. **Allocate within capacity → usage and dispatch packet.** Keep the entry's roles on the [worker route](../bg-build-with-me/references/worker-route.md). Agree the per-account project ceiling once; observe usage before material dispatch, at meaningful checkpoints and near the ceiling. Distinguish verified allowance from dated reports, estimates and unknowns. Keep explicit model and effort choices; never sum shared quotas. Apply [account and cloud continuity](../bg-continue-my-project/references/account-cloud-checklist.md) at limits. Qualified alternative providers, and any emergency pay-per-use cover, come only from the routes and authority recorded in the overlay's `ROUTES.md`. With a single provider, use its qualified subscription capacity. Never silently switch accounts or providers or buy capacity. Machine capacity is separate from account capacity: keep many workers thinking but only one heavy local run (full test suite or native build) at a time per machine, queued through `bg-heavy -- <command>`; build with focused tests and run the full suite once per candidate; when the machine is saturated, move independent packages to cloud workers that meet the [cloud checklist](../bg-continue-my-project/references/account-cloud-checklist.md).
4. **Dispatch and collect economically → exact job and result map.** Reuse current sessions and worktrees with disjoint ownership and accepted dependencies. Follow the [swarm lifecycle](../bg-finish-the-whole-job/references/swarm-procedure.md); `bg-swarm` launches, lists and stops local command-line workers. Send path-based briefs: pointers to files, commits and line ranges, never pasted logs, with one live-log path per job. Use one background wait and exact result pickup: no forwarding agent, polling or routine log dump. Keep full evidence in owned files and only essential errors and findings in the short result. Once per lead session, validate the actual job directory and completion-watcher path before relying on them; record the resolved paths and result, and hold the affected dispatch or wait if either is invalid. Treat a job queued over 5 minutes as stuck: reconcile its durable identity, then use `bg-governor queued --apply` to restart it once only when the recorded operation is mutation-safe; otherwise cancel and redispatch deliberately. Verify the exact repair target; keep failed and timed-out outcomes. Send consolidated same-owner repairs. Keep every finding under one stable ID through repairs and re-checks, and count repair rounds per package across resumes and handoffs (`bg-rounds`). After 2 rounds with findings open, stop and report the open IDs to the founder; round 3 needs the founder's explicit approval.
5. **Implement the smallest complete change → tested owned candidate.** Do mechanical steps under about 2 minutes yourself instead of dispatching them. Trace the affected flow and callers; repair the cause. Prefer existing helpers, native features, the standard library and installed dependencies. Keep validation, accessibility, observability, recovery and requested behaviour. Run risk-appropriate meaningful checks; rerun after relevant changes, failures or uncertainty, and reuse unchanged exact-version evidence. Integrate continuously into one tested head; keep the independent whole-candidate check separate from builder checks.
6. **Use supported efficiency controls → tool receipt and fallback.** Use a command-output filter for supported external commands and cached reads or selective compression when useful (for example RTK or Headroom, if installed). Keep the original output and retrieve it for exact diagnosis. Run shell built-ins and unsupported commands normally. Never filter tiny output, stack lossy compression or replay a mutation to get another log. Use a context-compaction hook only through a verified compatible hook or an authorised saved-copy route. Preserve native compaction, complete tool call/result pairs, scope, owners, authority, holds, versions, findings, uncertain effects and the next action. Use actual context telemetry at a useful boundary; never invent a percentage or edit an active transcript. Prepare installed efficiency tools and supported connections automatically, without duplicate services, installs or permission changes, and load a tool's guidance before operating it; `doctor plugins` shows what enabled plugins add to every session.
7. **Return concise evidence → handback and continuation checkpoint.** Keep the project checkpoint to one page ([template](../../templates/CHECKPOINT.md); about 1,500 words, within BGZFLOW_CHECKPOINT_KB) of current state: outcome, a single CURRENT RULES block, an OWNERS block, candidate, open findings, holds and next actions. Move history into `ARCHIVE.md` beside it; never delete it. Start a fresh chat or thread for each stage from a handover of BGZFLOW_HANDOFF_KB (2 KB) or less, and before the transcript passes BGZFLOW_CHAT_MB. State results, proof, gaps and next owner and action in short sentences in the user's language: 1–3 sentence progress updates and a short result with evidence links, with more detail when correctness or a requested explanation needs it. Keep exact errors, quantities and uncertainty. Record output reduction separately from subscription usage, elapsed time and money; claim an improvement only with comparable measurements. Apply the shared [evidence boundaries and record procedure](../bg-check-it-before-release/references/enforcement.md): source guidance, discovered tools, body reads and successful execution each need separate evidence.

## Red-flag thought → required action

| Thought | Required action |
|---|---|
| "Shorter means skip a requirement or test." | Keep the full outcome and meaningful checks; remove repetition. |
| "I'll read these big files to find where this lives." | Sync the code map, query exact names and read only the needed lines. |
| "The map came back empty, so there's no caller or test." | Empty is not proof: search with targeted `rg`, read the source and record the gap. |
| "The lead must reread every worker log." | Put heavy inspection on a worker job; return concise candidate-bound results. |
| "Every worker runs the full suite locally, to be safe." | One heavy local run per machine at a time, through `bg-heavy`; workers use focused tests; the full suite runs once per candidate; overflow goes to cloud workers. |
| "I'll paste the log into the brief so the worker has it." | Give a pointer to the canonical log path and line range. |
| "A selected skill is already loaded." | Obtain that executor's body read and tool evidence separately. |
| "Another poll will make it finish." | Keep the single background wait and pick up the exact result. |
| "Installed means compaction ran." | Record the actual hook receipt or the native fallback. |
| "Fewer output tokens prove money saved." | Compare measured accepted outcomes; label unavailable usage and cost. |

## Filled worked example

The [swarm procedure's worked example](../bg-finish-the-whole-job/references/swarm-procedure.md#worked-example) applies this skill to a notes app: path-based briefs with one background wait each, fast worker checks, one full run through `bg-heavy`, one consolidated repair within the two-round cap, and no saving claimed without telemetry.
