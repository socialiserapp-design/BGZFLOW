# Routing and caching

Choose locally for ordinary work. Reuse a selection while task, stage, capabilities and relevant inputs remain unchanged. Reconsider at a real change of task or approach, not every shell command. A failed optional router falls back to the current agent without blocking its reply. Honour the owner's disabled automatic paid Jev setting; explicit on-demand requests remain separate.

Choose a capable model using observed task outcomes, actual availability and the user's quality/time/usage preference. A cheap failed attempt plus repair can cost more than a successful stronger model. Independent parallel work may benefit from workers; simple sequential work usually does not. Include worker setup and result review in cost.

When the application owns the model API request, keep unchanged instructions and tool definitions stable, put changing task data later, and use the provider's documented caching support. Measure cache reads and writes separately from uncached input. Reordering tools or rewriting old history can break useful caching. Caching discounts input; it does not remove context occupancy or guarantee a cheaper task.

Requesty-style auto caching means provider-aware cache breakpoints and cost accounting, not a new requirement to route through Requesty. Claude/Codex host-managed requests are outside a Markdown skill's control. Do not change endpoints, accounts, permissions or spending limits to claim this feature is active.

Reuse exact local computations only when input, workspace and relevant environment match. Any answer cache additionally needs user/team isolation, source freshness and invalidation on corrections. Do not reuse uncertain external effects or private answers across users. Do not retry an unknown paid action until its actual outcome is reconciled.
