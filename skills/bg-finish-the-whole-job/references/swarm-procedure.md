# Coordinate independent work into one result

Use this procedure when parallel work is useful, under [the shared rules](swarm-rules.md).
It is not a requirement to create a swarm. One owner remains accountable for the
whole requested outcome; an integration writer may be that same owner.

## From agreed outcome to one candidate

1. Recover the original goal, latest corrections, current state, authority,
   pending effects and actual available capacity. Keep a concise current brief.
2. Identify shared interfaces and genuinely independent contributions. Verify
   external facts that affect the design. Name owners and needed checks.
3. Prepare suitable owned workspaces or output locations. Preserve existing
   changes and identify the input version. Use appropriate isolation for shared
   resources, without treating a worktree as a security boundary.
4. Supply each ready contribution with the relevant brief and method bodies.
   Dispatch through an existing supported route within observed capacity.
   A necessary prerequisite can be used after its relevant contract and behavior
   are checked; it need not wait for unrelated final integration.
5. Confirm actual execution and collect native results. Prefer completion events
   to repeated polling. A timeout, missing response or dead process is not proof
   that external effects stopped. Reconcile before retry or reassignment.
6. Workers implement complete contributions, run meaningful affected checks,
   and return actual results, limitations and needed shared changes. No fixed
   testing-skill trio, receipt form or per-job audit call is required.
7. One owner integrates contributions in dependency order, resolves conflicts
   without discarding required behavior, and checks the combined candidate.
   A branch existing or merging cleanly does not prove integration success.
8. Exercise the requested end-to-end outcome and relevant failure/recovery paths
   on the actual environment. Run appropriate combined tests once the candidate
   is ready; reuse valid evidence and rerun affected checks after changes.
9. Obtain independent scrutiny where the task or consequences require it.
   Preserve original failures and open findings; send specific repairs to their
   owners and verify closure on the corrected candidate.
10. Complete already authorized delivery, check the live result and report useful
    proof and remaining limits. Ask only for a real unresolved choice or authority
    gap. A product release follows its own current release policy.

## Route controls

Use the host's actual supported dispatch, message, wait, result and continuation
interfaces. Check their current contract rather than inventing a portable command.
See [worker routes](../../bg-build-with-me/references/worker-route.md).

Preserve enough native identity to distinguish the current job from older work.
Before resume, confirm ownership, target and pending effects. If an old writer
cannot be safely continued, reconcile it before creating a successor. Never
manipulate host state to force a desired session.

### Host-native subagents

A worker needs current context regardless of whether it inherits history.
Give it the actual workspace and limits; spawning a child does not move it into
a worktree or prove permission inheritance. Use only useful parallelism within
real account and host capacity. User-owned chats are created only when requested.

### Cloud work and gaps

Cloud execution requires an authorized supported route, appropriate repository
and secret scope, actual remote capacity and a verified return path. Local
background work does not continue while its machine is off.

Use the existing approved transport for exact commits or artifacts. Fetch and
inspect the actual return before integration. Do not assume local ignored files
or current uncommitted instructions reached a remote worker. Do not grant push,
broaden repository access or buy capacity merely to make a lane available.

## Worked example

For an agreed notes feature, storage and UI may proceed independently after
their shared data and error contract is known. Each owns different files and
checks its behavior. The integration owner combines them and exercises saving,
reloading and a storage failure without losing entered text.

If the combined failure path loses text, retain the failed observation, repair
the cause and recheck the affected flow. An independent check, when needed, uses
the corrected complete candidate and original user requirements. No fixed number
of workers, review models, waves or receipt records is implied by the example.
