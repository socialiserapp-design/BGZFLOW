# Brief, result and repair context

Supply enough context for the assigned executor to finish a useful contribution
without assuming it inherited the lead's history. Reuse existing task records
and native messages. These sections are optional structure, not required forms,
byte limits or an extra approval process.

## Plan template

The user's current outcome and decisions; relevant facts and unknowns; authority
and holds; shared interfaces; useful independent work and its owners; meaningful
success checks; current next action.

## Task row

Outcome and inputs; prerequisites and actual version; owned files or resources;
relevant method bodies and tools; scope and permissions; expected output and how
to verify it. Include only applicable fields. Native execution identities are
recorded when observed, not invented before launch.

## Worker prompt

Give the actual contribution, current corrections and why it matters to the
whole result. Explain necessary dependencies and ownership boundaries. Supply
selected methods that fit this task; do not require every worker to read the
same testing or efficiency guides.

The brief does not override higher-priority user instructions or host permission
limits. State existing authority and exclusions accurately; do not silently add
account changes, spending, publication, uploads or customer-visible restrictions.

Prefer source pointers and concise evidence excerpts where available, while
ensuring the executor can actually access necessary context. A remote worker
does not automatically receive ignored local files. Do not include secret values
or unrelated private history.

Choose model/effort from the current task and actual capacity. Do not impose
fixed tiers, escalation on every failure or automatic paid audits. Use a fresh
independent checker when the task or consequences require one.

## Dispatch and pickup

Use supported native tools and preserve the actual execution identity.
Confirm the job began and collect its actual result. Prefer event-based
notifications; do not add a polling daemon or five-minute replay rule.

On timeout, interruption, absent response or a dead process, reconcile the
original job and pending external effects before retrying or moving ownership.
Do not assume a cancelled command stopped every child or reversed its effects.

Preserve explicit user requirements for worker visibility and messaging. A sent
message is not proof that it was read or acted on. If a required decision is
missing, ask through the supported route while continuing independent safe work;
elapsed time is never approval.

## Worker handback

Return a concise account of what changed, actual checks and their results,
the candidate or artifact, remaining findings, uncertain effects and next action.
Use enough detail to assess the result; there is no ten-line cap, mandatory
confidence label or receipt command.

Keep relevant original evidence accessible. Distinguish native, fixture,
headless, physical-device and unrun checks. Passing a component test is not
whole-product success, and missing real-platform proof stays unverified.

Report shared changes that need another owner. Preserve unrequested customer
behavior as a scope issue; do not hide it behind a technical implementation note.

## Consolidated repair

Combine actionable findings for each owner, including earlier unresolved ones.
Name the corrected behavior and what evidence will close it. Repair on the
actual candidate, preserving unrelated work and current user decisions.

Use the exact supported continuation or reconcile the old writer before a
successor handoff. Recheck affected behavior and relevant integration without
resetting history or forcing a new review council. Follow actual project repair
limits rather than inventing a global round counter.

## Mailbox field

Use an existing mailbox or bridge only when the task or user requires it and
the host supports it. Include the correct recipient and current context.
No mailbox, extra observer or communication service is required by this template.
