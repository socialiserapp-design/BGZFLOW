# Shared swarm rules

These rules have a local [swarm gate](../../../docs/swarm-gate.md). Every workflow uses `node "${CLAUDE_PLUGIN_ROOT}/tools/swarm-gate/swarm-gate.mjs"`: start one ignored ledger with approved resources/limit/reserve, wave zero and pieces; reserve dispatches; record every outcome/deferral, candidate, ordered check and finding. Claude hooks enforce recognizable launches and production releases; other leads must use the same CLI before the action. Blocks go to the lead with one next step. Permission questions cover raising usage, a third wave and emergency release override; post-diagnosis failures are reported with recommendations. Records cannot prove honest testing: inspect handback proof and run the whole test.

At admission, record each piece goal and the agreed acceptance script. At phase 0 show the provider-neutral light/standard/heavy-write/heavy-read mapping and preference order in the same resources/usage question; save the chosen private policy. Rediscover aged/version-changed/removed/default-changed models through `swarm-resources --refresh-models --policy FILE`, then run `swarm-gate refresh-models` after start. New exact settings need small approved/account-bound qualification jobs within the non-reserve budget. Help is not proof. New dispatches may adopt qualified changes under the user's opt-in; running jobs keep their settings. Unavailable routes fall back at the same tier after the old writer is dead and work preserved.

Optional Jev judgment is off publicly. Code decides exact rules; one bounded sanitized batch can block definite semantic violations, warn the AI lead on ambiguity and fall back to code with a warning on errors. It detects reworded retries, duplicate work, weak build/fix briefs, improper requests to the human and missing journey coverage. It never approves or grants authority, never reads credentials and never automatically retries a paid call. Record response usage, model and elapsed time. See the gate guide for thresholds and config.

At phase 0 ask for resources and usage together: Small 8 jobs/4 worker-hours (reserve 3/1.5), Medium 20/12 (5/4), Large 48/32 (8/8), or custom numbers. `start` saves both defaults as next time's recommendations. A readable provider allowance may add a percentage cap; otherwise label it unavailable. Current nonsecret login observations must match account/environment proofs; stale, unknown, ambiguous and logged-out identities cannot reuse cached qualification. Proof metadata never comes from reading credentials. Status uses project plus normalized goal/slug/task ID or saved GOAL and sorted owned files; summary fallback is visibly weak. Keep completed/failed result lines and the record containing them through deduplication.

Open every repair batch through `record fix-wave`. Advance owned branches to the **failed combined candidate**, preserving commits/dirty work and verifying ancestry, before dispatch. Merge every repair, pin the new SHA, then real-platform golden journeys and rollback, never another review. Release preparation dispatches independent prep together, waits for every build before dependent captures, and verifies one assembled packet against SHA, version, build IDs and hashes.

Read once before the first active `/swarm` family step in a session. Apply these rules with the [swarm procedure](swarm-procedure.md). Commands are public and model-neutral: providers, accounts, model/effort choices, paths and dispatch controls come from the private overlay `ROUTES.md` and the host's qualified route. A command grants no new release, spending or access authority.

## Resources: ask once, use the approved set

1. **Discover and ask once.** Run `node "${CLAUDE_PLUGIN_ROOT}/tools/swarm-resources/swarm-resources.mjs" --swarm <task-id>`. Show installed, authenticated or proven state, cost and gaps. Recommend only proven routes, including a prior selection where still proven. Ask the founder one multi-select question, then save the explicit answer with `--swarm <task-id> --approve <id1,id2,...>` and checkpoint it. Approval is scoped to workspace and swarm; another swarm's set is only a recommendation. Nested fix/check/ship reuse this approval and the persistent wave count. Approved unproven routes get one small qualifying job before real work: prove entitlement, effective access/model/effort, environment and exact return. Save the passed dated result with `--save-proven <proof.json>`; see the [proof contract](../../../tools/swarm-resources/README.md). Reuse only matching account/environment/capabilities. Installation, authentication, a cloud home, overlay `Qualified: yes`, and resource approval alone never prove readiness. Read-only `/swarm-status` needs no approval.
2. **Spread ready work across every approved suitable resource.** Prefer qualified cloud workers for heavy portable pieces; local workers handle devices, emulators, local databases or signing. Apply the [cloud checklist](../../bg-continue-my-project/references/account-cloud-checklist.md): verify included entitlement, repository/environment access, sole ownership and return evidence. Keep additional spend zero unless authorised. Name blocked or unused resources and why; never force an unsuitable lane to occupy a slot.
3. **Checkpoint limits, then fill proven capacity.** Before dispatch record measured concurrency, dated account allowance/reset, the agreed project ceiling and a reserve for checks and up to 2 fix waves. Label unknowns and qualify missing limits before real work. Count shared local/cloud quotas once. Build independent ready pieces together within these limits and dependencies, refill as slots free, and queue one heavy local run at a time through `bg-heavy`. Before reassignment, cancel the old attempt, verify terminal state and fence its writer/process tree or remote write authority. Preserve commits/dirty work, reconcile durable operation IDs, then transfer ownership in the checkpoint before dispatching on another approved proven resource. Never silently add an account/provider, buy capacity or bypass a hold or host policy.
4. **Use proven routes and effective settings.** Load [BG Build With Me](../../bg-build-with-me/SKILL.md), [BG Efficiency](../../bg-efficiency/SKILL.md) and the [worker route](../../bg-build-with-me/references/worker-route.md). Discover supported dispatch/status/wait/resume schemas. Local CLIs may use `node "${CLAUDE_PLUGIN_ROOT}/tools/bg-swarm/bg-swarm.mjs"`; other routes come from the overlay. Carry the route's exact model/effort settings into builds, repairs, reviews and cloud jobs, and verify the returned effective settings; defaults are unverified. Verify filesystem, approval, internet, login and required services before calling a job running. Save full history and exact identities. Use one supported background wait and exact pickup; no polling service or routine transcript dump. Preserve command exit codes and capture output once: filter the saved output, never rerun a job to recover hidden evidence. Convert brief paths to the worker's native absolute format at shell/platform boundaries (for example `cygpath -m` where supported).

### Dispatch checkpoint and cloud transport

Before each wave checkpoint wave-0/candidate SHA, approved resources, limits/reserve, owners and exact working directories, findings, persistent fix-wave count and pending effects. Save returned job/task/thread IDs, invoking session and return branch immediately, before any next action. Update on collection, cancellation, integration and compaction. Match every resume against this record and the latest job in that exact directory; a mismatch needs a fresh scoped successor after fencing and reconciling the old writer.

For cloud work, commit transportable context before pinning wave 0, or embed the brief and full required skill text in the supported cloud task. Excluded local context folders do not travel. Under existing push authority, push `<wave0-sha>:refs/heads/wave0/<swarm>` to the approved remote, qualify repository/environment access, launch on that branch and record the cloud task ID. Verify the worker starts at that SHA. It commits and pushes to its owned return branch (for example `cloud/<slug>`) and returns the exact commit. Fetch the branch and confirm that commit exists; if push is unavailable, reconcile and use the supported commit/patch transport with identity proof. Collect cloud contributions untouched. One integration writer merges them with all other contributions before any whole tests or review; the lead does no per-cloud-piece review or test.

## Build whole

5. **Wave 0 pins contracts and acceptance.** One owner prepares shared dependencies and commits interfaces/types, API/data shapes and migrations, approved UI tokens, shared configuration, disjoint ownership and the runnable acceptance script to the integration baseline. Record the wave-0 SHA, contract hashes, requirement/decision IDs, skeleton and baseline failures. Every worker branch starts there: `git worktree add <path> -b workers/<slug> <wave0-sha>`; never omit the start-point. Repairs retain their prior admitted commits. The script names every customer step and expected result, including failure/retry, access, accessibility, money, recovery and devices; Android includes visible constrained-device test, repair and retest. Code dependencies use admitted exact commits.
6. **One owner per file, one integration writer.** Every writer gets an owned worktree, cloud branch or non-code output location. Shared manifests, routes, lockfiles and config belong to the integration writer; workers request shared changes in their handback. Preserve unrelated dirty work and other leads' jobs.
7. **Workers build quality in.** Every build/fix worker must read and use `test-driven-development`, `systematic-debugging` and `verification-before-completion`, plus current/next domain guidance. Resolve installed bodies through host discovery, record hashes and actual reads, and provide verified read-only copies when needed; never add third-party bodies to this plugin. If unavailable, name the gap and apply equivalent [pack methods M1–M3](../../bg-build-with-me/references/capability-coverage.md#pack-methods): failing test first, trace root cause before fixing, fresh proof before completion. Label a fallback manual, never a claimed skill read. Run only fast checks on owned/touched files, never the full suite or a shared test database. Leave no placeholder production paths; commit on the owned branch. Return 15 lines or fewer with exact candidate, changed paths, commands/results, evidence pointers/hashes, confidence `high / medium / low` with a reason, assumptions, blockers and requested shared changes. Keep full proof in owned evidence files and follow the [worker packet](worker-packet.md).

Run the jev-audit skill on your own diff when jev-codes is installed; fix confirmed findings in the same job and retain before/after findings and reported usage. Skip missing tooling. Return a structured handback with exact base/return SHA, job ID, saved fast-check output, actual exits and matching counts. `record piece` admits it only after deterministic proof checks and optional Jev test-goal/claim-output questions. Rejection returns to the same worker and counts toward failed-twice. Ambiguity goes to the lead. Admission and workers' quality work are not independent reviews or whole-review fix waves.
8. **No per-piece reviews, full runs or deploys.** Build every piece before assessing the combined result. Fast checks prove a built contribution, never acceptance. Show one explicitly labelled early working skeleton where required, then the integrated result. The founder must not discover bugs by using a journey presented as finished.

## Then test whole

9. **One integration per candidate.** After every piece returns, one writer combines exact commits/artifacts, including untouched cloud contributions, in dependency order, preserves both behaviours in conflicts, applies shared changes and verifies accepted `DECISIONS.md` IDs. Pin candidate SHA/configuration/live-like environment. Run the full suite once in its own pinned checkout, through `bg-heavy` locally. Reuse only that exact evidence in `/swarm-check`.
10. **Real-platform rehearsal, then one review.** Rehearse the exact frozen candidate on preview/staging/hidden production with matching runtime, bindings, database version, secrets and real provider accounts; money in test mode. Run golden journeys and one rollback, capturing actual output. The lead dispatches one fresh read-only review per stable release ID. Only reproduced wrong money, data loss, security/privacy or missing rollback blocks. Reviewer design and all other findings go after-launch. A builder never dispatches its own reviewer.
11. **Two fix waves; rehearsal proves repairs.** Return reproduced blockers to the same workers under stable IDs. Re-integrate and pin a new SHA, then rerun real-platform journeys and rollback until passing. Never a second independent review or review of a repair. After two waves, send open blockers and a recommendation to the founder; a third wave needs recorded chat authority.
12. **Finish and switch on.** The lead accepts passing rehearsal with no open reproduced blocker; no ready verdict or founder acceptance of a review. For customer-visible changes, the final step is the founder checking the verified build on a phone or capable device: only their approved-design mismatch blocks on design. Record the result against the SHA. Under existing release authority, switch accepted work on for all intended customers, watch live errors for one hour, then keep it or switch off and fix forward. Built-but-off is not done. Keep actual evidence, limits and next owner/action.

Classify cheaply first. Environment/access/login and flaky infrastructure need lead remediation, without model escalation; unclear contracts go to the lead and only a product choice to the human. Code/logic and unknown causes require one heavy-read diagnosis with Cause/Evidence, optionally one approved proven different-family diagnosis in parallel. The one following repair uses heavy-write and includes that note; a further failure is reported to the human with a recommendation. Escalated jobs still consume the limit. Quota/rate, network, provider outage and cancellation do not count as logical failures. The two-wave cap concerns findings from the lead's independent whole-candidate check, not a worker's quality work during build.
13. **Proof before done.** Nothing is done until the complete acceptance script and required checks pass. The lead accepts a `ready` whole-candidate verdict itself and records it; never ask the founder to accept a review. Keep worker completion, record consistency, candidate acceptance, release authority and production verification separate.

## Communication and release

14. **Three short reports.** Report plan/resources dispatched, all pieces combined, and finished with proof, in 8 lines or fewer each. Give estimates as ranges. Checkpoint exact state, holds, gaps and next owner/action. Ask only for unsettled product/design/business choices, spending, release outside the brief, an unavoidable human step or serious findings after two fix waves.
15. **One authorised whole release.** Follow [BG Ship and Recover](../../bg-ship-and-recover/SKILL.md). Require the accepted exact candidate, passing checks and no blocking finding. Before deployment prove the release artifact's accepted SHA/build ID/hash/configuration and compatible rollback; production need not already run the new version. Deploy once under explicit authority, then verify production identity and actual whole journey, including failure/retry and money paths. Roll back on failed production checks. Publishing, payment, store submission, live trading, customer messages or data deletion require the brief to name them. Resource approval or passing tests grant no release authority.

If `${CLAUDE_PLUGIN_ROOT}` remains literal, resolve the installed plugin folder containing `commands/`, `skills/` and `tools/`. Runtime overlays and state remain private; never copy their identities or values into public files.
