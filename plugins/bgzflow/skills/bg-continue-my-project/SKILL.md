# Continue the project

Recover the original objective, latest corrections, settled choices, owners, retained work and unfinished actions from the native conversation and automatic continuity state. Read exact source messages when a summary is ambiguous. The latest user instruction governs the affected scope; unrelated settled decisions remain valid.

Retrieve other-session history only on demand, with a focused query when the current task actually needs it; native hooks do not inject other chats automatically. Treat retrieved material as a partial, source-linked view: consult original messages when a choice or permission depends on missing detail, and verify the current project record. A code graph helps locate relationships; it does not establish current user decisions, ownership or completed work. See the plugin's docs/project-recall.md for retrieval limits. Do not make duplicate manual records of events the host already captures; update the existing concise project brief when the outcome, decision or next owner changes.

Use native compaction in the same chat. After compact or resume, check that the current task, selected methods, important decisions and pending operations are present before dependent work. Restore missing detail from retained records. Do not make the user start a new chat to satisfy a byte threshold.

Match the actual project, branch, running process, account and worker before changing anything. Historical status is not live state. A process identifier alone is not proof that the intended server is running; check its executable or entry point, address and observable behaviour where applicable.

Reconcile an interrupted external action under its original identity before any retry. Preserve the first result and failed evidence. If the effect cannot be determined, hold only the affected action and continue independent authorised work.

Reuse useful existing work. Repair the smallest complete causal boundary, rather than recreating a project or rerunning a completed paid job. If the host or provider has changed, verify its available capabilities before choosing a replacement route.

Resume the next requested unfinished step and verify its real effect. A status question requests a status answer, not a new build or a cleanup operation. Explain any missing access or physical step plainly.

A selected skill supplies a method, not extra permission. Follow the user's latest request, existing decisions and host permissions. Use the shared task context and native tools; do not create a parallel tracker or demand paperwork. A method being selected or loaded does not prove its result.

## Use the existing record path

Native foundation hooks capture supported messages and tool events automatically.
Use that retained evidence and the current project brief; do not reconstruct a
second transcript or ask the user to copy context. Some hosts cannot capture every
operation. State the missing evidence and reconcile the actual effect.

Applications embedding BGZFLOW can use `createFoundationSession` to preserve
confirmed requests, answers, decisions, assignments and observations through the
trusted host adapter. That API is an integration facility, not a command sequence
ordinary chat agents must manually fill. See `docs/foundation-session.md` in the
source package for the actual contract and limits.
