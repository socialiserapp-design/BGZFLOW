# Research the decision

State the question whose answer could change the work. Inspect existing project code, records, installed packages and available services first. Identify what is known, what is uncertain and what evidence would resolve it.

Search appropriate primary sources: current vendor documentation, original papers and implementations, standards, official records and actual system observations. Community discussions can reveal problems and ideas; verify consequential technical claims against original sources or a reproducible check.

For build-versus-reuse choices, compare relevant existing packages by capability, compatibility, maintenance, licensing, integration effort and cost. Inspect the original implementation when its actual behaviour matters. Choose custom code only where there is a concrete need; an attractive name or benchmark does not prove fit.

Proactively identify gaps between the user's intended outcome and the actual available capabilities, including tools needed to verify the result. Do not wait for the user to name a missing package. Search suitable existing implementations, evaluate privacy and required access, and recommend the smallest adequate option. When installation or adaptation is already covered by the task's engineering authority, carry it out and verify real operation; do not stop at a list of suggestions. Ask before new spending, sensitive access, a material product trade-off or other action outside authority. If a gap remains, state its practical effect and continue work that does not depend on it.

Use a broad enough search to expose alternatives and disagreement, without a fixed number of websites or mandatory research ritual. Stop when additional investigation is unlikely to change the decision. Explain unresolved evidence rather than manufacturing certainty.

Return a recommendation, supporting sources, trade-offs and the implication for this task. Keep dates/versions and applicability clear. Discovery alone does not justify installation or scope expansion; the option must meet the actual task and existing authority. Do not add background research, scheduled scans or automatic new permissions.

A selected skill supplies a method, not extra permission. Follow the user's latest request, existing decisions and host permissions. Use the shared task context and native tools; do not create a parallel tracker or demand paperwork. A method being selected or loaded does not prove its result.
