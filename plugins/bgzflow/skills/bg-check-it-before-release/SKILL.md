# Check the real result

Recover the original request, consequential answers, intended users/environment and promised result. Identify the exact candidate and the current running version. Assess the whole requested outcome, not just a convenient file, checklist or unit test.

For a comprehensive product, feature or change audit, use the relevant coverage from [full-spectrum audit](../bg-full-spectrum-audit/SKILL.md), including independent product challenge, undiscovered needs, better concepts, approved designs, architecture alternatives and actual cross-platform outcomes. This supplies expertise to the existing review, not a second release gate. Use [Expo testing](../bg-expo-testing/SKILL.md) when Expo automation is a suitable way to obtain mobile evidence.

For consequential or complex work, use an independent checker with access to the request, candidate and evidence. The checker should reproduce behaviour and inspect sources; it must not simply endorse the builder's explanation. A different provider is optional, not proof of independence or correctness.

Use checks proportionate to the change. Exercise the relevant actual browser/device/service and inspect its resulting state. Confirm the server or app instance used by the user is the one tested. Include the applicable failure, retry and recovery behaviour. Use test accounts and provider test modes where relevant.

For source-based work, check that the important claims follow from applicable sources and that quoted material, dates, jurisdiction or versions match. For calculations, independently recompute meaningful totals. For creative work, assess the agreed audience, constraints and intended use; do not pretend a machine score settles taste.

Preserve failures and missing evidence. A test that did not run, unavailable device, stale screenshot or guessed process is unverified. A command exiting successfully, a selected skill or a model-written report cannot substitute for observing the promised effect.

For each material finding, apply the existing review's
[shared impact ratings](../interrogate/references/impact-ratings.md): separate
harm 1–10 and how often 1–10, or unknown with the missing evidence. State
confirmed/probable/unverified, exposure scope and period, affected people/data/money,
recovery, urgency and next action. Prioritize real consequences and strong evidence,
not reviewer votes. This adds no review round, numerical release gate or permission.

Fix demonstrated defects and recheck affected behaviour. Run the appropriate combined tests once the candidate is integrated. Do not rerun unchanged suites or create another review cycle without a concrete reason. Never weaken a test merely to obtain a pass.

Report the outcome, useful proof, remaining limitations and next action. Separate a working component from the completed objective. Release only within existing authority; a passing review does not grant it.

A selected skill supplies a method, not extra permission. Follow the user's latest request, existing decisions and host permissions. Use the shared task context and native tools; do not create a parallel tracker or demand paperwork. A method being selected or loaded does not prove its result.
