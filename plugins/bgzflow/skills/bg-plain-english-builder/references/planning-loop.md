# Planning that evolves with the conversation

Use the [shared questioning procedure](question-round.md#procedure) for this skill, `grill-me` and `4x4`; they contribute methods to one conversation. For substantial work, keep a [short current brief](plan-template.md#optional-short-working-brief) in the project's existing record. A simple answer needs no plan, interview or new document. Preserve original decisions and update only the parts changed by new evidence or instructions.

## Current and next expertise

Use BG Efficiency when efficiency guidance helps; read its [sources](../../bg-efficiency/references/sources.md) only when their detail matters. Consider relevant [capability coverage](../../bg-build-with-me/references/capability-coverage.md), then use the [available selector](../../bg-build-with-me/references/skill-selection.md#supported-foundation-entry-points). Reuse a valid selection during unchanged work. If routing is unavailable, the current agent selects relevant methods and continues. Read the selected guidance before dependent work; supported automatic capture records delivery and tool events without a manual receipt.

Use planning guidance for relevant interfaces and requirement coverage, and domain guidance for established names and edge cases. Fold useful [interview methods](../../bg-build-with-me/references/optional-methods.md) into the shared question procedure. Current user instructions, applicable answers and host permissions govern the work; imported methods do not add routine approvals, fresh-chat loops or duplicate records. Revisit selection when the stage, scope, platform or risk changes materially, not on every message.

One accountable owner maintains the user's intent. Use a single agent for connected work or independent workers through the [worker route](../../bg-build-with-me/references/worker-route.md) when useful and supported. Supply the outcome, owned work, relevant decisions, limits and checks. Inspect actual results; no two-minute delegation threshold, fixed byte cap or compulsory separate worker applies.

## Research without a reminder

Inspect retained evidence and relevant code first. When capability, compatibility, licensing, cost or maintenance affects a decision, verify it in dated primary sources. Treat videos and examples as leads, and confirm consequential claims in authoritative documentation or code. Record unavailable evidence and the work it affects. Stop a research branch once it supports its decision. Never install or run a discovered repository just to show activity.

Keep four sources distinct: the founder's actual answers, facts from inspected code, sourced external facts and assumptions. Record the exact source, version and inference. A code default describes current behavior; it does not establish the founder's preference. When evidence contradicts an assumption, correct it in the same ledger and carry the change into affected tasks and tests.

## Coverage and stopping rule

Use these categories as prompts for finding consequential gaps, within the four shared areas: outcome, approach, practical delivery and failure. They are not mandatory rows or questions. For non-software work, substitute the domain's equivalents.

| Category | Establish before dependent work |
| --- | --- |
| People and situations | Audience, context, need and exclusions |
| Complete journey | Entry, core job, result and cross-surface continuation |
| Content/output quality | What useful, correct output means; what is unacceptable |
| Priorities | Whole outcome, sequencing and explicit deferred scope |
| Visual and interaction | Chosen experience, rejected alternatives, actual approval |
| Platforms and devices | Required surfaces, capability gaps and native checks |
| Accessibility | Applicable input, reading, motion and assistive needs |
| Identity and permissions | Who acts, who sees data, limits on consequential actions |
| Privacy and data lifetime | Collection, storage, deletion and cross-device expectations |
| Money and margin | Business model, customer price, fees, costs and existing spend authority |
| Failure and recovery | Offline, interruption, retries, uncertain effects and restoration |
| Operations and support | Who maintains the product, observes failures and helps users |
| Success measures | Observable useful outcome; acceptable quality and performance |
| Acceptance and release | Prototype decision, skeleton, whole-product return, the founder's involvement and standing holds |

Ask about consequential unresolved outcomes, product choices and trade-offs using the [question procedure](question-round.md#procedure). Give enough context to make an informed choice. Derive routine engineering from evidence instead of handing it to the user. Reuse applicable answers; investigate discoverable facts yourself.

Before declaring the overall understanding complete, check for important omissions across the promised outcome. Keep asking while an unresolved choice could materially change that result, even after sixteen questions. Do not ask irrelevant questions to fill categories or turn coverage into a form. The next independent authorised action may proceed once its own material choices are resolved; unresolved dependent work stays explicit. A deferral preserves the affected requirement and revisit trigger. Revisit the relevant questions when evidence changes. Examples are illustrative, never substitutes for actual answers.

## Prototype interface

Use a clickable prototype when it resolves a consequential product uncertainty. For an unresolved new look, use [BG Personal Product Design](../../bg-personal-product-design/SKILL.md) to compare a proportionate range of genuinely different [rendered directions](../../bg-personal-product-design/references/techniques.md#eight-or-more-rendered-directions). Vary the dimensions relevant to the decision; no fixed count applies. Fit each look to the product and its audience; there is no universal dark or glass house default. A small change reuses the genuinely approved design.

Give the UI owner the relevant surfaces, journey, content, states, accessibility needs, existing decisions and open choices, as in [resolving a design choice](plan-template.md#resolve-a-real-design-choice). The [design guidance](../../bg-personal-product-design/references/design-contract.md#useful-design-context) connects these choices to [evidence of the requested result](../../bg-personal-product-design/references/design-contract.md#evidence-that-answers-the-users-request). Continue independent work without a second UI kit or repeated taste research. Each surface follows its own conventions: a chat surface uses equivalent text actions and truthful status rather than imitating a desktop layout.

The UI owner returns a runnable click path plus representative empty, loading, success, error, offline, cancel and permission states, marks what is simulated, and shows the actual versions under consideration. Record the founder's exact choice and its scope. Then pin the approved tokens, components, interactions, reference images and surface versions through the design contract. Lock only a look the founder actually approved; a generated screenshot or silence is not approval. Carry rich effects on capable devices, and reduction of only the affected effects on constrained devices, into the implementation checks.

## Complete execution handoff

Use the [short brief](plan-template.md#optional-short-working-brief), shared [glossary](../../bg-build-with-me/references/glossary.md) and an appropriate [dependency view](../../bg-finish-the-whole-job/references/work-graph.md#task-schema) when coordination needs them. Preserve existing requirement and finding references. A worker needs the outcome, owned scope, dependencies, current decisions, meaningful checks and return route. Name concrete files and commands when known; do not invent them or require a formal schema for ordinary work.

Honour existing spending limits and the task's quality, time and usage priorities. Ask only when a material trade-off remains unresolved. Check actual availability before dispatch; a new budget form or reserve is not required. Use a single worker or authorised independent workers through [BG Finish the Whole Job](../../bg-finish-the-whole-job/SKILL.md), keeping one lead and one writer per shared change. Return an early usable slice when helpful. Use [independent checking](../../bg-check-it-before-release/SKILL.md) where consequence or the project policy requires it.

Keep original asks, corrections and their observed status visible in the existing record; [check the whole result](plan-template.md#check-the-whole-requested-result) before claiming completion. Distinguish implemented work, observed effects and unverified gaps. Test counts and worker claims alone do not prove the user's outcome. A separate checker, when required, examines the actual candidate and evidence. Do not add an extra report or review to every reply.

Use supported native execution and event notifications. Keep current ownership and pending effects; reconcile the original job before retry. Choose independent checking by consequence. Preserve findings across repairs and apply the task’s actual repair limits. A persistent failure needs diagnosis, not a universal round cap or permission to discard scope. Continue already authorised next steps when checks pass.

Apply the [shared enforcement reference](../../bg-check-it-before-release/references/enforcement.md) once, at the material handoff. Record native, manual, fixture and unrun evidence separately. Send needed changes to shared contracts or enforcement to their owner through the handback.
