# Tool harmony: use the tool that answers the question

Prefer a supported tool already available for the task. Avoid overlapping services,
repeated model calls and mandatory startup demonstrations. A tool's installation
does not prove it is active, accurate or appropriate for this work.

## Useful divisions of work

| Need | Suitable approach | Boundary |
|---|---|---|
| Choose relevant expertise | Foundation catalogue and Jev, or main-agent selection | Selection grants no authority and proves no application. |
| Locate code, callers and tests | Existing maintained code index where useful; targeted search and reads | Empty index results do not prove no callers or tests exist. |
| Locate decisions and history | Existing project records or host search | Preserve current decisions and distinguish old instructions. |
| Read source | Bounded relevant sections and actual callers | Do not infer unseen code or strip context needed to understand it. |
| Filter long output | Existing supported filter, including RTK or Headroom when appropriate | Preserve recoverable original evidence; do not hide failures. |
| Reuse a complex script | Existing source file or a scoped saved script | Check inputs, authority and original operation identity before rerunning. |
| Count or compare exact values | Ordinary deterministic tools | Counts are not proof of product behavior. |
| Choose effort and workers | Current task, actual capacity and consequence | No fixed provider or highest-effort default. |
| Preserve context | Native continuation plus supported foundation restoration | No 2 KB handoff requirement or transcript-size-triggered fresh chat. |
| Run builds and tests | Existing project runner within observed machine capacity | No compulsory queue helper or unknown hosted spending. |
| Track execution | Native job identity, existing task records and notifications | No mandatory receipt, startup-check, grading or league command. |

Use these approaches where needed, not as a required sequence for every request.
Routine questions may need none. An existing project index can save reading, but
search is a first-class option and should be used directly when it answers the task.

## If a code index is already in use

Check the worktree, candidate and index freshness before relying on it. Synchronize
after relevant edits or branch changes according to that tool's actual interface.
Inspect source around the returned symbols and cross-check dynamic boundaries.

Give workers the actual entry points, contracts and affected tests. A checker
inspects the whole relevant change and original request, including callers outside
the edited files. Test suggestions from an index are not executed test coverage.

Keep one owner per index or shared change. Do not introduce a new index engine,
Git hook, daemon or MCP server merely because this reference mentions it.
CodeGraph, graft and other tools are alternatives when already available and
suitable; old comparative measurements are not a permanent winner for every task.

## Output and evidence

Keep replies concise without dropping the user's requested explanation or meaningful
proof. Preserve original failed evidence. Use a short current account of the
candidate, checks, outcome, uncertainty and next action in existing records.
Do not demand a separate handback receipt or make the user read internal logs.

Only claim savings from comparable observed work, accounting for retries,
integration and checking. Smaller output or an enabled compressor alone does not
prove reduced cost or better quality.

## Host behavior

Use the host's documented, currently supported model, effort and permission
controls. Do not copy dated settings from another host or assume that a local
setting reached a worker. Changing a model or installing a plugin does not by itself
prove activation in an existing session.

Native compaction is the default. Use additional context tools only if they are
useful, supported and authorized; do not edit live transcripts or stack lossy
compressors. If a capability is unavailable, state the specific gap and continue
independent work through an existing suitable route.

Keep secrets out of prompts, logs and tool arguments. Never broaden access,
silently change accounts, start duplicate services or retry an uncertain external
effect to satisfy this guide. Actual user instructions and host permissions govern.
