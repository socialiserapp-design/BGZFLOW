# Learning and measurement

Prefer the installed TokenEconomizer for its repository lessons, supported reversible tool selection and repeated-failure intervention. Do not run a second BGZFLOW model judge or lesson-mining job for the same failure. Inspect actual host support: modern deferred tool discovery may already avoid the cost an older pruning rule assumes. Unused is not proof a tool is unnecessary; keep recovery possible.

Use BGZFLOW's native learning bridge for source-linked task/outcome proposals where the application has configured evaluators. Preserve user/team privacy. A proposal or confidence score is not adoption: compare against retained failures, working cases and unfamiliar cases using the owner's existing evaluator. If no evaluator exists, keep it unverified and continue the task; do not manufacture a self-certifying check or background paid campaign. Withdraw regressions and retain rollback.

Record available observations locally through existing event records, without a required model-written report after every turn. Distinguish guidance delivered, tool actually used, output bytes, hook delay, model calls, failed/retried work and verified outcome. Where billing is available, include fresh input, cached input, cache writes, output, workers, routing and learning. Otherwise label the measure as bytes, estimated tokens or latency, never actual money saved.

Observe ordinary work first. Compare like tasks and environments when evidence permits; do not announce a percentage saving from one compressor counter. A smaller response that causes another search or an incorrect decision can increase total cost. Preserve test quality and the user's finish line while reducing duplicate work.
