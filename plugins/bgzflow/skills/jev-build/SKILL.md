# Build with Jev

Choose locally first. For a justified Jev consultation, use the installed `judge --stdin --live` helper with a stable `taskId` from the original task brief. Reuse that identity across follow-ups, workers and compaction; do not generate a new identity to obtain another call. The helper allows one attempt and reuses an identical successful answer. On failure, uncertainty or changed input after use, continue locally and ask before another paid request. Do not use the multi-pass catalogue router or bypass the helper with a direct SDK call. Embedding applications must enforce the same budget in their trusted execution layer.


Start from the requested behaviour and inspect the existing application. Read the
relevant current official docs and [shared method](../bg-jev/references/methods.md).
Reuse the packaged official SDK and existing connection path for BGZFLOW; an external
application should use its established dependency/configuration conventions. Do not
copy a second HTTP client, install demo hooks or import an entire example app.

Write the decision logic first: which observations determine which allowed result,
including unknown, absent evidence and failed service. Jev supplies only the inputs
that need language/image judgment. Keep math, exact matches, permissions, execution
and recovery in code. Keep question wording, criteria and combination policy easy
to inspect and test. For explanatory requests, explain without scaffolding files.

Use Noul, Choice, Score or experimental Box as appropriate. Preserve the full answer
distribution, model and usage across the service boundary. Never turn a timeout or
authentication failure into a valid answer or silently switch providers. Keep keys
server-side, respect cancellation and give interactive requests a bounded timeout.
Batch independent questions; serialise only genuine dependencies. Consider images
only when layout/appearance is necessary, the data disclosure is authorised, and
the experimental limitation fits the task. Long context is opt-in, not a substitute
for relevant evidence. Neither option changes host permissions.

Use the existing test suite. Offline transport tests establish wiring; live public
or authorised examples establish actual endpoint behaviour; representative and unseen
cases assess usefulness. Compare with the current implementation and count the full
workflow's latency, cost and failures. Keep permission and spend changes with the
user; don't demand repeated approval for already authorised steps. Current model
aliases move, so retain the returned version and evaluate upgrades before depending
on old thresholds. Don't promise guaranteed truth, self-training or universal speed.
