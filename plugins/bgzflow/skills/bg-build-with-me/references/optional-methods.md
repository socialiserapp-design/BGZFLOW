# Optional methods under BG trigger ownership

Useful methods from public skill collections fit inside BG routing, and a whole skill can be adopted when it fits. Keep one entry router ([BG Build With Me](../SKILL.md)), one [glossary](glossary.md), one [shared contract](decision-and-delivery-contract.md) and one [worker route](worker-route.md). Each method below is described as a capability, so the pack works without any extra skill installed. Names are discovery hints; verify the actual source and licence of each installed skill. BGZFLOW’s root licence does not relicense third-party methods. This map changes no live hook and is not a recommendation to disable that collection.

## Whole skill versus extracted method

"Whole" means read the full body and apply its relevant guidance under higher-priority user and host instructions. "Extracted" means use the named method under BG's contract and discard the conflicting workflow. Include third-party bodies only with compatible licensing, attribution and authority; same-name copies need not be identical. Follow [selection and delivery](skill-selection.md#selection-and-delivery). A method review does not certify helper scripts or prove a tool ran. Reading a method does not authorise every action in it.

## Living alongside another methods framework

The following procedure applies only when the user has authorised installing or changing workflow integration. Merely loading another framework does not authorise editing its hooks, entry files or skills. During ordinary work, resolve conflicting guidance under the current task and leave installation alone. For an authorised integration change:
1. Inventory the framework's version and its start, clear and compact injections alongside the host's own entry files. Back up the exact before-state and keep the existing supported wake and compaction controls.
2. Use one startup entry that loads BG's compact router and baseline and restores missing or changed context. Route method selection through the table above. Remove competing "always start a second workflow" instructions from that entry while keeping the useful methods available. Use only a supported, owner-controlled hook or entry mechanism; never edit a plugin cache or add a loader.
3. Bind each trigger once: discovery owns new product choices, capability coverage owns stage and platform floors, delivery owns dispatch, and verification owns independent inspection. The founder's original scope and recorded decisions outrank imported defaults.
4. Retire duplicate or unsafe startup skills only after reconciling actual discovery paths, with a backup, preserving unique source and history.
5. Qualify fresh, cleared, compacted and resumed lead and worker sessions: actual body loading, one router, no duplicate interview, board or review chain, retained holds and a native compaction fallback. Record live versus staged status, and roll back a startup change that makes behaviour worse.

## Final UI polish and new looks

Use a final polish pass on affected UI screens when appropriate (see [final polish](../../bg-personal-product-design/references/techniques.md#final-polish)). The BGZFLOW design method or an approved specialist can supply it. Read selected guidance, then apply the parts relevant to the actual change and current decisions. Treat fixed fonts and layouts as one style option and preserve an approved look. Execute any claimed code or randomisation for real, only when relevant and authorised; never invent its output or hide overflow to conceal a defect.

For an unresolved new look compare a proportionate range of [genuinely different directions](../../bg-personal-product-design/references/techniques.md#eight-or-more-rendered-directions). There is no universal dark or glass default. An approved look changes only by the founder's decision. Keep rich effects on capable devices and reduce only the affected effects on constrained devices. The relevant capability guidance never invents style presets.
