# From worker result to real use

Use this loop for one agent or several. It supplements the existing project record and release policy; it adds no new tracker, universal review round or release authority.

1. **Set the real finish line.** Recover the latest user decisions and identify the actual audience, installed app/service, intended devices, meaningful journey and resulting effect. Keep a physical device, simulator, browser, service request and source test distinct. A later user decision can change the required surface; preserve its scope rather than applying it retroactively. Investigate conflicting project records against the original decision and notify their owner.
2. **Own every transition.** Name who builds, integrates, installs and checks the result. One person may fill several roles. Give a worker the relevant current decisions, owned files, dependencies and expected evidence. Keep deployment with its authorised owner. A worker who cannot deploy returns the candidate, what was actually checked, unresolved findings and the remaining real-use check; it does not claim the product is finished.
3. **Receive and act.** Use the existing host/job system to preserve assignments and correlated results. Verify that a completion reaches the accountable lead. When a result arrives, inspect its candidate and evidence, handle the appropriate independent review, then integrate or return a concrete correction. Do not leave ready work waiting for an unrelated batch. A notification, file, timer or idle worker is not acceptance. If the host cannot wake an idle lead, state that specific limitation and use its supported wait/continuation route while available; do not promise unattended operation that has not been tested.
4. **Check the combined candidate.** Reconcile concurrent changes and exercise the behaviour they affect together. Check schema, wire protocol, persisted data and installed-client compatibility where relevant. Run the appropriate local tests, preserving failures. Identify the exact artifact and configuration that will be installed. Later changes invalidate only the evidence they affect; they do not inherit a previous candidate's pass automatically.
5. **Put authorised work into use.** Once the project's required checks pass, install or deploy through its existing supported route and within the user's authority. Reuse standing approval for the agreed target. Apply [ship and recover](../../bg-ship-and-recover/SKILL.md), including its relevant platform procedure. Do not confuse a successful publish, download or restart request with the target actually running that artifact. If access or authority is missing, continue independent work and state the specific remaining step.
6. **Observe the result.** Read back the running version and relevant runtime/configuration on the intended surface. Exercise the actual user journey and inspect the resulting data/service effect; include relevant failure and recovery behaviour. Check existing data and older supported clients when affected. For a repair, reproduce the formerly failing journey on the originally affected surface. Screenshots can support UI observations but cannot establish invisible backend effects.
7. **Keep the existing record honest.** Link the request and worker result to the integrated candidate, deployed artifact, observed surface, exercised journey, effect and evidence date. Distinguish **built**, **delivered/installed** and **used successfully**; stop the claim at the weakest unverified link. Record the next owner/action for incomplete steps. Before yielding, advance ready transitions and preserve the supported continuation route, outstanding effects and current user decisions.

## What can and cannot prove success

- Unit and component checks can prove their tested behaviour. They do not establish that an installed product uses the code.
- HTTP success can prove an endpoint responded. It does not prove mobile compatibility, adoption or a customer journey.
- A worker's report is a claim to inspect. A compiler result, passing workflow or generated audit is not independent product acceptance.
- A simulator run is real execution on that simulator. It does not establish physical-device behaviour, permissions, sensors or an installed customer's state.
- Observing the intended app complete the requested journey, with the authoritative effect checked, supports that scoped result. It does not prove every product feature or every future condition.

## Enforcement boundary

Portable skills guide the agent. Hooks can preserve events and supply context, but cannot force every host to dispatch, wake, deploy or observe a device. Use the supported routes already available for ordinary app work and report missing capabilities. Only when host integration is itself within the authorised task, connect the existing BGZFLOW foundation to trusted execution and observation callbacks. Validate that integration through the whole loop on its actual host: worker finishes, lead receives the result, correct artifact reaches the intended app, journey and effect pass, and failure recovers. Until then, label each unconnected step as an integration gap rather than claiming guaranteed autonomy.
