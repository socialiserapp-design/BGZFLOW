# Shared rules for useful parallel work

Use parallel agents only when independent contributions or a fresh assessment
improve the current outcome. A tightly coupled task may be better completed by
one capable agent. These rules add no fixed team, provider, approval round or
paperwork command.

## Resources and authority

- Check actual available tools, models, account capacity and shared resources.
  Model names do not establish access or independent allowances.
- Use existing permissions and current user decisions. Ask only about a material
  unresolved quality/time/usage choice, spending or access outside authority.
  Do not ask again merely because a new stage or group of workers starts.
- Choose enough workers for useful independent work and integration capacity;
  do not fill every slot simply because it exists.
- Preserve explicit requirements for visible sessions and communication. Use
  supported host routes; do not create bridges, timers or helpers just to qualify
  a task. Unavailable capabilities are specific gaps, not blanket project stops.

## Build complete contributions

- Preserve the original request, current decisions, shared interfaces and
  meaningful success criteria. Verify consequential external assumptions.
- Keep one writer per shared change, contract, device or release candidate.
  Isolate parallel edits where needed. Worktrees do not isolate permissions,
  credentials, processes or external services.
- Assign a complete usable contribution and its relevant checks. Avoid an
  attractive UI shell disconnected from the behavior the user requested.
- Deliver relevant selected methods to the executor. No worker must load a
  fixed trio of skills, produce read receipts or obey a ten-line handback cap.
  Use test-first or debugging methods when appropriate to the actual work.
- Preserve unrelated work, original failures and uncertain external operations.
  Reconcile the same operation before retrying or transferring ownership.
- Build only the authorized behavior. Surface an unrequested customer-facing
  wait, refusal, cap or hold as a scope problem; do not introduce it silently.

## Integrate and verify

One owner combines contributions in dependency order and identifies the actual
candidate. Check affected contracts and real end-to-end behavior. A successful
worker result does not prove the combined product.

Use focused checks during work and the required combined checks after integration.
Reuse unchanged valid evidence; rerun what changed. Avoid repeating full suites
after every file or banning a necessary integration check until an arbitrary stage.

Use an independent checker when the task or consequence requires it, with original
requirements and access to the exact candidate. A different provider is optional.
Retain findings across repairs; recheck affected behavior instead of resetting
the evidence or adding an unnecessary review cycle. Honor the task's actual
repair limits and current release policy.

## Communicate and continue

Keep a short current account of ownership, native execution identities, relevant
results, gaps and next actions in existing records. Preserve original evidence.
No swarm ledger, confidence field, grade or model-written success form is required.

Continue through native compaction, restoring decisions and selected methods.
Do not force a fresh chat at every stage or by file size. On interruption or
account exhaustion, reconcile in-flight work before a supported continuation.

Release only within existing authority and after applicable checks. Confirm the
intended installed/running version and real outcome after the switch. Money,
data, privacy, recovery and explicit user holds remain protected. A record, review
or resource choice never grants additional spending or release authority.
