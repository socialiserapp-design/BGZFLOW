# Shared methods

These instructions are neutral method bodies. Read only the section linked by the selected entrypoint. They do not add tools, permissions or background services.

## Understand and plan

Interpret short prompts, examples and corrections using the current conversation and relevant permitted project records. Separate the requested outcome, settled choices, routine implementation choices and unresolved decisions. Preserve the latest user direction; do not turn a suggestion or example into a requirement.

For a straightforward request, carry out the work directly. For substantial work, state a compact outcome and the observable result that would demonstrate success. Inspect existing work before proposing replacements. Ask a focused question only when a material ambiguity cannot be resolved from available context; continue independent work meanwhile.

Discover relevant available methods, tools and permitted data for the task. Read a method before applying it; selection alone is not application. Use existing interfaces and artifacts where suitable. Compare alternatives only when the choice matters to the outcome, considering capability, reliability, integration, cost and maintenance. Verify consequential external assumptions through the research method before relying on them.

Make a proportionate plan of complete usable outcomes with dependencies and meaningful checks. Keep the user's scope and authorization intact. Execute authorized work rather than ending with a plan when action was requested. Report the result against the original outcome, evidence, unresolved limits and the next action if needed.

For substantial work, retain the user's original intention and latest corrections separately from the implementation checklist. Trace every material requested result to its evidence and target user/environment. Check that the checklist still covers the whole request before treating its passes as completion. Use an existing goal/verification mechanism where available; a missing mechanism does not justify narrowing the goal. Resolve missing material choices, while making routine engineering decisions yourself.

Supply relevant professional knowledge instead of expecting expert prompting. Investigate how the desired experience could be achieved, including useful established systems the user may not know exist. Explain a materially better option in plain English: what it enables, why it fits, its main trade-off and your recommendation. Ask the smallest consequential question when a choice changes the product; reuse settled answers and continue independent work. Clear wording, a long prompt or a high clarity score alone does not establish that the actual need or architecture is understood.

Translate the user's wording into the task's shared vocabulary and contracts, reusing existing project definitions. This applies across subjects, including architecture/design, marketing, research, professional work and everyday tasks; it is not a fixed software dictionary. Retain the original phrases, their source, the agreed concept and its observable meaning in context. Define overloaded terms with a concrete scenario when useful; for example, agree what automatic updates must do before selecting an event or polling design. Give each worker the same relevant definitions/version and requirement references. Preserve the user's meaning through handoffs and call out contradictory interpretations. Keep private records within their permitted project/role boundary; a shared vocabulary does not imply shared access to all data. Do not require a global taxonomy or formal glossary for a simple task.

When using the shared engine, put relevant definitions in the existing goal contract's `vocabulary` before starting workers: `domain` and `entries` containing `term`, `userWording`, `meaning`, `sourceRef` and optional `scope`. The engine carries that snapshot in the saved method context; do not merely name a glossary that workers never receive. Distinguish a user's explicit meaning from your proposed interpretation in the existing brief, and resolve a consequential ambiguity before relying on it. Reuse the saved meanings on resume; a new catalogue or another agent's preferred wording must not silently replace them. If the user changes a meaning, explicitly revise the active goal and retain the prior version; do not continue obsolete definitions or silently replay previous effects.

For software product work, cover the applicable dimensions: functional integration, deployment and customer access, real user journeys and state read-back, error handling/recovery, security/privacy, reliability/performance, accessibility/visual usability and maintainability. Derive the checks from the product and its risks; a small edit does not require a full-product ceremony. Rehearse the actual configuration and customer environment, repair discovered defects, and observe the release within existing authority. Record unavailable or unverified dimensions and residual risks; do not assert that any test suite proves absence of all bugs. On Turn 1 run `bgz egm xray` (6-stage system lifecycle X-Ray), `bgz egm autosetup` (zero-bottleneck tracing/map setup), `bgz egm mentor` (anti-sycophancy co-architect + plain-English architecture lessons), and `bgz eval research` (4-Channel x 4-Angle open-source discovery so existing permissive tools/packages are downloaded or forged via `bgz skill-forge` instead of built from scratch). Lock the spec through the Stateless 6-Lens Goldfish Pre-Code Gate (`bgz egm goldfish` -> `codeUnlocked: true`) before writing implementation code. Run Step 0 Pre-Mortem (`PREMORTEM`) before coding each vertical slice: list ways the slice could fail, rank risks with `bgz jev`, and write the catching check first. Compile the slice graph with `bgz graph compile` and emit a 3-Line Plain-English Best-Practice Advisory (`Why it fits + Main trade-off + 1 core concept`) when a better industry standard or MIT/Apache-2.0 library applies. Before handback run `bgz eval run` and `bgz egm drift` to block hallucinations, math slips, reward-hacking test skips, and truncated responses.

## Research and check

Identify the question or claim that could change the answer or action. Discover relevant permitted sources: supplied files, structured records, connected private data, existing artifacts, authoritative publications and live systems where available. Use the closest primary evidence appropriate to the claim; a website is only one source type. Do not infer access or a tool capability from a method name.

Inspect the supporting passage, record or actual result. For important claims, retain source identity, relevant date/version and what it supports. Distinguish direct observation, source-backed statements and inference. Check applicability, freshness and material contradictions; explain unresolved disagreement instead of hiding it. A citation alone does not establish support. Stop searching when further work is unlikely to change the decision, and state unavailable evidence without inventing certainty.

For an artifact or action, define the intended effect before checking it. Inspect the produced artifact or read back actual state in the intended environment. Verify relevant failure, retry or recovery behavior when warranted by risk and authorization. A successful command, selected method, submitted request or passing isolated test is not proof of the complete outcome. Use independent checking when required or meaningfully useful and available; identify self-checks honestly.

Keep evidence tied to the version and environment checked. Reuse unchanged evidence and recheck affected behavior after a repair. Distinguish prepared work, a reached surface and a verified real effect. Report missing or failed checks with their practical limitation; do not claim completion beyond the evidence. During independent verification (`independent_verifier` with builder reasoning stripped via `bgz graph context`), run Step 2 Jev Attack (`ATTACK`): fan out Jev checks across content/inputs, hostile prompt injection, failure injection (timeouts, retries, idempotency, no double-charge), regressions and cost before transitioning to `complete`.

## Continue and recover

Recover the original outcome, latest corrections, settled decisions, retained artifacts and last reliable evidence from the conversation and relevant permitted records. Read targeted sections instead of replaying all history. For status-only requests, report the reconciled state without starting new work.

Compare recorded state with current observable state. Distinguish planned, implemented, checked and actually used work. Preserve existing work and useful failure evidence. Identify the exact affected task, artifact, session or operation and any active owner before changing shared work.

A timeout or interrupted response leaves the effect uncertain. Inspect the original operation identity and actual destination state before retrying any action that could duplicate a charge, publication, message or other mutation. Continue through supported tools and existing authorization. If identity or access remains unavailable, explain that bounded gap and continue unrelated ready work; do not invent a successful recovery.

For a failed portable-engine goal, use its existing recovery API or `bgz engine recover` with the same goal, a stable repair ID and an authorised corrected command. Retain the original failed operation, acceptance criteria and shared meanings. A repeated repair keeps its original identity; settle unknown earlier effects through the actual host before starting another effect. Choose and execute a routine repair within the user's existing authority without asking the user to restate it. Verify the repaired result against the original outcome. After 2 failed fix attempts on the same slice, stop retrying the same approach: trip `advisor_circuit_breaker` and run `bgz graph assess` (`ASSESS, RESEARCH, ADAPT`) to classify the failure (`spec|decomposition|method|tool|model|test`), identify the cross-round root cause, research across platforms, record a changed method/plan and Context Graph precedent, log a lesson via `bgz lessons add`, and propose skill updates via `bgz jev improve`.

Resume the next unfinished authorized step, reusing valid decisions and evidence. Restore relevant method guidance if missing. Keep a short checkpoint when it will help continuation: outcome, current facts, unresolved effects, artifacts/evidence and next action. Verify the resumed result before reporting success.
