# Automatic selection, preparation and actual use

Six public synthetic native outcome cases use ordinary requests without method,
supplier-skill or helper-script names. They cover local sound synthesis, supplied
SVG assembly, investigation/build/verification without a formal plan, a consequential
offline payment repair, a simple reply and paused-work follow-up recovery.

This extends the existing native foundation harness. It reuses `buildConfig`,
native hook preflight, the installed promptfoo providers and an independent
read-only semantic judge. No runtime hooks or separate scheduler are added.

## Run

From the project drive, set the same explicit environment choices as the foundation
suite: `BGZ_EVAL_PROVIDER`, `BGZ_EVAL_MODEL`, `BGZ_EVAL_JUDGE_PROVIDER`,
`BGZ_EVAL_JUDGE_MODEL`, and optionally `BGZ_EVAL_CODEX_PATH`, `BGZ_EVAL_EFFORT`
and `BGZ_EVAL_WORK_ROOT`. Keep workspaces and evidence on the build drive.

```
node --test evals/automatic-use/automatic-use.test.mjs
node evals/automatic-use/run.mjs --live --plugin <reviewed-built-plugin> --output <fresh-owned-directory>
node evals/automatic-use/run.mjs --live --plugin <reviewed-built-plugin> --plugin-id bgzflow@bgzflow-candidate --output <fresh-owned-directory>
```

Without `--live`, no model call starts. `--cases local-sound,simple-reply` can select
a subset. Existing evidence is never overwritten; each case retains native
preflight, response, actual workspace, independent owner probes, timings and the
first failure. No silent retry occurs. Codex uses its actually installed plugin;
`--plugin` is the reviewed comparison/replay source, not an instruction to silently
install or trust it. `--plugin-id` defaults to `bgzflow@bgzflow-live`. For an alternate
identity, worker, independent Codex judge and native preflight receive the same
quoted flat `cli_config` activation overrides: candidate enabled, live disabled.
Nested objects are deliberately avoided because the installed provider's flattener
does not quote `@` keys. Preflight requires the exact candidate hooks trusted and
enabled, refuses another active BGZFLOW copy, resolves actual hook commands and
compares native package version and every reviewed file against `--plugin`.
Prepared method evidence must also match the actual candidate-cache identity and
reviewed body digest; a same-version home copy cannot stand in for it.
Claude uses the explicit local plugin through its existing provider.

Candidate staging/installation and native trust are external prerequisites. The
runner does neither. The current native install API has no initially-disabled
option, so this harness does not claim a candidate can be installed globally
without activation or that a preset disabled flag is preserved. Resolve a supported
inactive staging method before a pre-deployment candidate run. Do not copy login
files or weaken hook trust to make staging work.

The recovery case currently requires Codex. Its first native turn pauses before
edits, then the runner reads the **actual returned** thread identity and supplies
the provider's supported `thread_id` to resume with the correction. Missing resume
identity fails as unverified. Neither turn is fabricated or concatenated. This is
paused-work interruption/follow-up recovery, not forcibly killing an in-flight
tool, a new provider session or native compaction.

The investigation/checking and risk cases allow named legitimate alternatives
in owner-only grading; the native requests do not contain those names. This
avoids equating one preferred method title with successful expertise.

## Required source evidence

`RouteSelected` proves a selection was recorded. `MethodContextPrepared` with
`delivery.methods[]` records `{id,name,version,bodyDigest,characters,provided:true}`
only after the actual operative body has been prepared in host additional context.
This suite does not equate that event with cognitive reading. Missing adapter
evidence is **unverified delivery**, not proof the artifact is wrong. Deferred
metadata alone never passes. Root owns implementing this source event; these
fixtures do not forge it during native runs.

Sound and SVG additionally require successful observed execution of their actual
existing helpers. The saved outputs must pass independent structural/effect
checks; merely mentioning a helper or echoing its name does not count. Script
invocation alone also does not establish success. Other cases use real saved
effects plus source-attributed stage records and a semantic judgment. A stage
test that uses a formal plan does not pass the no-plan path.

## Decisive checks and limits

- Audio: valid non-silent PCM, exact three-second stereo duration, activity near
  supplied contacts, quiet gaps, six actual family files, and independent replay
  of editable cue source against the actual stem. Hearing comfort and subjective
  sound quality remain unverified without audition.
- SVG: actual geometry/order, duplicate hold, local ID/reference closure, title,
  one-shot/loop CSS and reduced-motion fallback. This is structural verification;
  actual rendered appearance/playback remains unverified without a renderer.
- Payment: unseen original/retry/conflicting-identity/independent-purchase/failure
  and invalid-amount scenarios execute the candidate and read its actual ledger.
  Echo-green, constant receipts and deduplication without conflict checking fail.
  This is an offline simulator, not a real payment integration.
- Every case compares the actual file set and original bytes against its permitted
  scope. Unknown observation coverage is stated rather than inferred from prose.
- Simple-reply elapsed time is retained without an invented universal latency
  target; no tool work or unrelated specialist selection is accepted.

Offline tests establish grader boundaries only. No native/provider run has been
performed for these new cases by the fixture author. They establish neither a
controlled plugin-versus-baseline improvement nor perfect skill compliance.
